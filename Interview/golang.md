Golang垃圾回收机制：

三色标记法：执行时都需要 STW （stop the world）, 暂停程序运行

1.  将所有对象标记为白色
2.  将所有根对象标记为灰色
3.  遍历灰色对象，把直接可达对象标记为灰色，并将自身标记为黑色
4.  重复第3步，知道标记完所有的对象
5.  回收所有的白色对象

如果不 STW，那么在标记和清除的过程中，程序可能会继续运行，这样可能会导致对象的状态发生变化，从而导致垃圾回收器无法正确标记对象的状态，最终导致回收错误。

若不使用STW，需满足其中一种：

1.  强三色不变式：不允许黑色对象引用白色对象 解释：如果一个黑色对象不直接引用白色对象，那么就不会出现白色对象扫描不到，从而被当做垃圾回收掉的尴尬。
2.  弱三色不变式：黑色对象可以引用白色对象，但是白色对象的上游必须存在灰色对象 解释： 如果一个白色对象的上游有灰色对象，则这个白色对象一定可以扫描到，从而不被回收

Golang实现：

1.  插入写屏障：当一个对象引用另外一个对象时，将另外一个对象标记为灰色。

满足：强三色不变式。不会存在黑色对象引用白色对象

1.  删除写屏障：在删除引用时，如果被删除引用的对象自身为灰色或者白色，那么被标记为灰色。

满足弱三色不变式。灰色对象到白色对象的路径不会断

解释：白色对象始终会被灰色对象保护

1.8以后：混合写屏障：

在垃圾回收开始时将栈上的对象全部扫描并标记为黑色（不进行二次扫描）

在垃圾回收期间任何栈上创建的对象都会标记为黑色，避免了二次扫描

在垃圾回收期间删除任何的对象都会标记为灰色

在垃圾回收期间创建的任何对象都会标记为灰色

互斥锁Mutex ：

互斥锁是一种最基本的锁，它的作用是保证在同一时刻只有一个 goroutine 可以访问共享资源。Sync包，使用 syns.Mutex 结构体来表示。互斥锁的性能开销较大，因为每次加锁和解锁都需要调用系统内核函数。

读写锁RWMutex是一种特殊的锁，它分为读锁和写锁。读锁可以被多个 goroutine 同时持有，但是写锁只能被一个 goroutine 持有。Golang 的 sync.RWMutex 是写者优先的，优先处理写的操作。

原子操作是一种不可分割的操作，要么全部执行成功，要么全部执行失败。在针对内存中某个值的操作时，原子操作可以确保在并发环境下不会出现数据竞争，其他 goroutine 无法在操作进行中对该值进行读写。

**互斥锁和原子操作的区别**

- 互斥锁通常用于保护一段代码，只有一个 goroutine 可以访问这段代码，其他 goroutine 需要等待， 而原子操作通常用于保护一个变量，确保在并发环境下对变量的读写是安全的。
- 互斥锁是一种悲观锁，它认为并发访问是一种常态，所以会在访问前先加锁，而原子操作是一种乐观锁，它认为并发访问是一种特例，所以会先尝试进行操作，如果失败再进行重试。
- 互斥锁是一种重量级锁，它会涉及到内核态的上下文切换，性能消耗较大，而原子操作是一种轻量级锁，它是在用户态完成的，性能更高。
- 互斥锁有操作系统的调度器实现，而原子操作则是有硬件提供的原子指令实现，无需加锁而实现并发安全。

**Java对比介绍⼀下Go语⾔的特点和优势**

1\. 语法简洁，开发效率高

Go 的特点：Go 语言设计简洁，没有复杂的继承、多态等概念，通过组合实现代码复用。

Java 的对比：Java 的语法较为冗长，需要大量模板代码，特别是在定义类和方法时。

2\. 内置并发模型

Go 的特点：Go 原生支持并发，基于 goroutine 和 channel 实现轻量级并发。Go 的协程占用资源非常少，可以轻松创建成千上万的协程。

Java 的对比：Java 使用线程模型实现并发，线程较为重量级，创建和切换的开销大。

3\. 编译速度快，运行性能高

Go 的特点：Go 使用静态编译，编译速度非常快，生成的二进制文件直接运行，无需虚拟机，减少了启动时间和资源消耗。

Java 的对比：Java 使用 JVM 运行字节码，尽管有（即时编译）优化，但启动速度比 Go 慢。

4\. 部署简单，跨平台方便

Go 的特点：Go 编译生成的二进制文件无需依赖运行时环境，能够在多种平台直接运行。。

Java 的对比：Java 程序需要依赖 JVM，部署时需要安装对应的 Jav运行环境，复杂度略高。

5\. 内置工具链丰富

Go 的特点：Go自带工具链（如go fmt, go build），开发流程非常简洁高效。支持代码格式化、测试、文档生成和依赖管理，减少了对第三方工具的依赖。

Java 的对比：Java 依赖于 Maven、Gradle 等第三方工具来管理构建、依赖等任务。

6\. 社区生态

Go 的特点：Go 的生态主要集中在后端服务、微服务和云原生领域，具有丰富的库和框架（如 Gin、Gorm、gRPC）。

Java 的对比：Java 的生态成熟且广泛，覆盖了企业级应用、Android 开发、大数据等多个领域，社区资源非常丰富。

7\. 内存管理

Go 的特点：Go 使用垃圾回收（GC）进行内存管理，但设计了较低延迟的 GC，适合高性能场景。

Java 的对比：Java 的 GC 功能强大，但在内存密集型应用中可能出现较长的暂停时间。

总结

Go 的优势体现在轻量级、简洁性和并发性能上，适合高并发、高性能的分布式服务开发，比如微服务、容器化应用等。而 Java 更适合大型企业级应用开发，特别是需要强大生态和复杂框架支持的场景。

### go包管理的方式有哪些？

Go Modules

目前 Go 的主流包管理方式是 Go Modules 模式，它也是 Go 包管理的标准和推荐方式。

这种模式下，Go都会将所有依赖模块下载到同一个缓存目录（pkg/mod）

在 Go Modules 中，go.mod 和 go.sum 是两个核心文件，分别用于管理项目的模块信息和依赖的完整性验证

1\. go.mod 文件

go.mod 是 Go Modules 的核心配置文件，记录了项目的模块信息和直接依赖（direct dependencies）的版本。

其中一般包含以下关键词：

module：声明模块的路径，通常是项目的仓库地址或自定义名称。loooo

go：声明项目使用的最低 Go 版本。

require：列出项目直接依赖的模块及其版本。

replace：替换某个模块依赖，可以指定本地路径或其他版本。

exclude：排除特定版本的依赖，避免使用有问题的版本。

2\. go.sum 文件

go.sum 是用于依赖校验的文件，记录了所有依赖（包括直接和间接依赖）的版本和校验信息（哈希值）。

当我们运行 go build 或 go get 时，Go 会检查 go.sum 中记录的校验和是否匹配下载的依赖内容。如果不匹配，会报错，防止构建受到恶意依赖的影响

3\. 二者的关系

我喜欢用类比的方式来区分它们间的关系：

go.mod 可以想象为一个购物清单，只列出你需要买的物品。

go.sum 是物品的详细收据和品质检验证书等，确保你拿到的物品是正确的且没有被篡改。

4\. 常用命令

go mod init // 初始化一个新的 \`go.mod\` 文件，声明当前目录为模块。

go mod tidy // 清理无用的依赖，自动添加遗漏的依赖，保持 \`go.mod\` 和 \`go.sum\` 的一致性

go get // 添加、更新或删除依赖。会更新 \`go.mod\` 和 \`go.sum\` 文件。

go mod verify //校验 \`go.sum\` 文件中记录的模块的完整性

### Go 语言的接口是怎么实现的？

在Go语言中，接口（(interface)是一种动态类型，允许定义对象的行为，而不需要指定具体的实现。它本质上是一个动态类型和动态值的组合。 Go采用鸭子类型的设计哲学，不需要显式声明实现关系。只要一个类型的方法集满足接口的所有方法，编译器自动认为该类型实现了该接口。也就是说.一个类型只需要定义接口要求的方法，就可以被视为实现了该接口。

### Go语言中如何实现继承？

### Go语言中如何实现多态？

在 Go 语言中，多态主要通过接口（interface）实现。接口定义了一组行为（方法），不同的类型通过实现这些方法来满足接口，从而达到多态的效果。Go 的接口采用隐式实现机制，即只要一个类型实现了接口中的所有方法，就认为该类型实现了该接口。

通过接口变量调用方法，实际执行的是具体类型的方法。

**多态**是面向对象编程中的一个基本特性，指同一接口可以在不同类型上表现出不同的行为。

- **接口是实现多态的核心**：通过接口定义行为，不同类型实现接口来表现不同的行为。
- **接口变量实现动态多态**：接口变量可以存储不同类型的值，并调用其对应的方法。
- **类型断言和类型选择**：在需要时，可以识别接口变量的具体类型。
- **泛型增强多态**（Go 1.18+）：进一步提高了代码的灵活性和复用性。

而切片是引用类型， 传参时只拷贝切片结构体，底层数据是共享的

当原 slice 容量 > threshold，进入一个循环，每次容量增加（旧容量+3\*threshold）/4。

控制让本身容量小的切片增长速度快一点，减少内存分配次数，而让本身是大容量的切片增长率小一点，更好地节省内存。

切片特性：

- **切片**是 Go 中的核心数据结构，基于数组实现，具有动态大小、可变容量、支持自动扩容等特性。
- 切片在 Go 中提供了比数组更加灵活和方便的操作。
- 切片的底层结构由**指针**、**长度**和**容量**组成，且切片是引用类型，多个切片可以共享同一个底层数组。

### Map、Slice作为参数传递会遇到什么问题？

**1\. 数据被修改**

**map** 和 **slice** 是引用类型，所以当它们作为函数参数传递时，函数接收的实际上是它们的引用。所以在函数内部对它们的修改会直接影响原始值。

那如果希望保护原始数据，我们需要显式地进行深拷贝：

- 对于切片，可以使用 copy 创建副本。
- 对于 map，手动遍历键值对创建新的 map。

**2\. 容量扩容引发的切片引用失效**

如果函数内部对切片进行了 append 操作并触发扩容，切片可能指向新的底层数组，而原始切片的内容不会受到影响。

**3\. Map 的并发安全性**

map 在多个 Goroutine 中并发读写会引发运行时错误，这是因为map本身没有考虑线程安全，并发读写会导致数据竞争 sync.Map 是并发安全的.

原生map没有加锁机制，多个协程同时修改可能导致哈希表结构破坏，，同时读写可能造成脏数据；另外runtime会检测map的并发不安全操作。

**4.slice也不是并发安全的：**

多个协程同时修改切片元素会引发数据竞争；另外切片支持扩容，并发读写可能造成引用不一致

在 Go 语言中，struct 类似于传统面向对象语言中的 class，可以通过组合和方法绑定实现类似对象的行为，但仍然存在区别：

Go原子操作和锁有以下区别：

实现原理上，原子操作基于CPU原子指令，无需操作系统介入；锁通过操作系统调度机制，涉及用户态和内核态切换。

### Go 可以限制运行时操作系统线程的数量吗？

Go语言采用G-P-M模型进行调度，其中G代表Goroutine，是轻量级的用户态线程；P是调度上下文，代表处理器；M是操作系统线程。多个Goroutine可以复用少量的M，通过P来协调调度。

虽然Go没有直接提供限制操作系统线程数量的方法，但可以使用GOMAXPROCS环境变量或者runtime.GOMAXPROCS函数来设置同时运行的逻辑处理器的最大数量。由于每个逻辑处理器会绑定一个操作系统线程来执行Goroutine，因此限制逻辑处理器数量也就限制了操作系统线程的最大数量。

### ※Go 是 GC 算法是怎么实现的？

垃圾回收（Garbage Collection，GC）是一种自动内存管理机制，用于自动回收不再使用的内存，避免内存泄漏。在程序运行过程中，会不断地分配内存来创建对象，当这些对象不再被引用时，如果不及时回收其占用的内存，会导致内存占用不断增加，最终可能耗尽系统资源。

Go语言的GC算法基于标记清除算法，并使用三色标记法和写屏障技术实现并发标记。具体实现过程如下：

标记阶段采用三色标记法，将对象分为白色、灰色和黑色。从根对象开始，通过不断地将灰色对象标记为黑色，并将其未访问的子对象标记为灰色，最终完成标记过程。

为了保证并发标记的正确性，引入了写屏障技术。当对象的指针发生修改时，写屏障会记录这些修改，避免对象被错误地回收，确保新创建的对象或修改后的引用关系不会被遗漏标记。

标记准备阶段：暂停程序的执行（Stop The World，STW），初始化标记状态，开启写屏障。

并发标记阶段：垃圾回收器和程序并发执行，从根对象开始进行三色标记。

标记终止阶段：再次暂停程序的执行，完成标记工作，关闭写屏障。

并发清除阶段：垃圾回收器和程序并发执行，清除所有白色对象占用的内存。

白色对象是没有被访问过、没被引用过的，是垃圾对象；灰色是中间态，表示对象正在被标记（当前对象被发现但仍有子对象未标记）；黑色是已标记的对象，表示对象已经没有未标记的子对象。

在标记阶段结束后，会进入标记终止阶段，这个阶段会暂停程序的执行，完成一些收尾工作，如处理写屏障记录的信息等。

在GC过程中，支持并发和并行执行。并发GC可以让GC过程与用户程序并发执行，减少STW时间；并行GC可以使用多个线程同时执行GC任务，提高GC效率。

虽然Go语言的GC尽量减少了STW（暂停所有的用户协程）时间，但在标记开始和结束阶段仍然需要短暂的STW来保证标记的准确性。

第一次stw标记启动前的根对象，第二次是防止在标记完会出现对象改变、漏检等问题。

### ※Go 语言map和sync.Map谁的性能最好 ？

### Golang中init() 函数是什么时候执行的？

### Golang中Map的数据结构是什么？

### ※Golang中的sync.WaitGroup是什么？

在Golang中，sync.WaitGroup是sync包提供的一个用于等待一组goroutine执行完成的类型。它内部维护了一个计数器，该计数器表示还有多少个goroutine未完成任务。

sync.WaitGroup提供了三个主要方法：Add(delta int)用于增加计数器的值，通常在启动goroutine之前调用；Done()用于将计数器减1，每个goroutine在完成任务后应调用此方法；Wait()会阻塞当前goroutine，直到计数器的值变为0，即所有goroutine都已完成任务。

sync.WaitGroup适用于需要等待多个goroutine完成任务的场景，如批量任务、并行计算、资源清理等。使用时需要注意，Add方法应在启动goroutine之前调用，Done方法必须在每个goroutine中调用，且不能在Wait方法之后调用Add方法。

### ※Golang中的sync包是什么？如何使用？

golang 中的sync包是一个用于解决并发编程中同步问题的标准库包，用于管理并发程序中的资源共享和避免数据竞争。这个包主要包含了锁(sync.Mutex和sync.RWMutex)、sync.WaitGroup、sync.Once(确保某个函数只执行一次，使用Do()方法调用需要执行的函数)、条件变量(sync.Cond)和其他同步工具。

在Golang中，除加Mutex锁外，还有以下几种安全读写共享变量的方式：

使用sync.RWMutex：读写锁允许多个协程同时进行读操作，但写操作是互斥的。适用于读多写少的场景。

使用sync/atomic包：提供原子操作函数，在硬件层面保证操作的原子性，适用于简单数值类型的增减操作。

使用channel：通过将共享变量的读写操作封装在channel的发送和接收中，以通信的方式共享内存，适用于多个协程之间需要有序处理数据的场景。

### Golang的并发模型是什么？实现并发的原理是？

Golang采用CSP（Communicating Sequential Processes）并发模型，其核心是通过通信来共享内存，而不是通过共享内存来通信。该模型主要基于Goroutine和Channel两个概念，Goroutine是轻量级线程，由Go运行时管理，可以轻松创建成千上万个；Channel用于Goroutine之间的通信和同步，提供了类型安全的数据传递方式。

Golang实现并发的原理基于G-M-P调度模型。G表示Goroutine，包含了执行所需的信息；M表示操作系统线程，是真正执行代码的实体，每个M都会被分配一个P，并从P的本地运行队列中获取G来执行；P表示处理器，负责协调G和M的运行。当创建一个Goroutine时，它会被放入某个P的本地队列，M从P的队列中获取Goroutine并执行。如果本地队列为空，M会从全局队列或其他P的队列中“偷取”任务，获取时采用批量获取的方式，通常会拿走全局队列中一半的goroutine。当Goroutine发生阻塞时，M会释放P，阻塞结束后Goroutine会被重新放入队列等待执行。此外，Go的内存管理系统为Goroutine提供了高效的内存分配和回收机制。

### Go中对nil的Slice和空Slice的处理是⼀致的吗？

在长度、追加元素、迭代等操作上，两者表现一致，长度都为0，追加元素都能正常工作，迭代时由于长度为0迭代体都不会执行。直接通过索引获取元素都会触发 panic ，nil slice和空slice赋值时会报错，追加不会

然而，它们也存在明显区别。nil的Slice没有底层数组，不占用额外内存，和nil判等为true；空Slice有底层数组，可能占用一定内存，和nil判等为false。并且空Slice可以通过make函数指定初始容量。

### Go函数中发生内存泄露的原因？

在 Go 语言中，内存泄露通常指的是程序在运行过程中分配的内存没有被释放，从而导致可用内存逐渐减少。

goroutine泄漏：goroutine启动后没有正确结束，如存在无限循环且无退出条件，会一直占用内存。

channel泄漏：发送数据到无缓冲channel但无接收操作，或接收channel数据时channel未关闭且无新数据，会导致goroutine阻塞，无法释放内存。

全局变量或静态变量持有大对象：由于其生命周期贯穿整个程序，若持有大对象且不释放引用，对象将一直占用内存。

缓存未清理：使用缓存存储数据时，没有合理的清理策略，缓存不断增长会造成内存泄漏。

### ※Go在循环内部执行defer语句会发生什么 ？

在Go语言中，在循环内部执行defer语句时，每个defer语句会被依次注册，但不会立即执行。当循环所在的函数返回时，这些defer语句会按照后进先出（LIFO）的顺序依次执行。

需要注意的是，如果defer语句使用了循环变量，由于defer语句会在函数返回时才执行，此时循环变量可能已经发生了变化。此外，循环中大量使用defer语句可能会导致内存占用增加，因为每个defer语句都会被压入栈中等待执行。

### ※Go的Slice如何扩容 ？

当向切片中添加元素时，如果切片的长度（len）等于容量（cap），再添加元素就会触发扩容。新容量大于原切片容量的2倍，则直接扩容。如果原切片长度小于256，则将容量翻倍。如果原切片长度大于等于256，则采用一个增长因子（约为1.25）来增加容量。

切片扩容时，会分配一个新的底层数组，将原切片中的元素复制到新的底层数组中，然后返回一个指向新底层数组的切片。原底层数组会被垃圾回收（如果没有其他引用）。

### ※互斥锁正常模式和饥饿模式有什么区别 ？

正常模式：偏向性调度，优先让已经准备好运行的goroutine获取锁，性能较好但可能导致某些goroutine“饥饿”。

饥饿模式：严格按等待顺序分配锁，确保公平性，防止“饥饿”现象，但可能会增加上下文切换的开销。

从正常模式切换到饥饿模式：当一个goroutine等待锁的时间超过一定阈值（通常是几毫秒），并且有其他goroutine正在持有锁时，Go会认为当前系统可能存在“饥饿”现象，于是将互斥锁切换到饥饿模式。

从饥饿模式切换回正常模式：当一个goroutine成功获取锁并且没有其他goroutine在等待时，或者当前持有锁的goroutine能够在短时间内完成工作并释放锁，Go会认为系统已经恢复正常，于是将互斥锁切换回正常模式。

### 函数返回局部变量的指针是否安全？逃逸分析和自动内存管理

在Go语言中，函数返回局部变量的指针是安全的。原因是Go编译器会做逃逸分析，若局部变量指针被返回或在函数外使用，编译器将该变量分配到堆上而非栈上。堆上变量由垃圾回收器管理，生命周期延长，直至不再被引用才回收，所以不会有悬空指针问题。

### ※在Golang中，Map可以边遍历边删除元素吗？

不过，需要注意的是，Go语言的Map不是并发安全的。在并发环境下，多个goroutine同时对Map进行遍历和删除操作可能会导致程序崩溃或出现未定义行为。如果需要在并发环境下操作Map，可以使用sync.Map或者使用互斥锁（如sync.Mutex）来保证线程安全。

### 在Golang中，删除一个key后，它的内存会被释放吗？

### ※简述一下内存逃逸？什么情况下会发生内存逃逸 ？

内存逃逸是指在Go语言里，原本应该分配在栈上的变量，由于某些原因被分配到了堆上的现象。内存逃逸是指在Go语言中，编译器通过逃逸分析，将原本可能分配在栈上的变量，由于其作用域超出函数或者生命周期需要延长，而分配到堆上的现象。

函数返回局部变量的指针。

局部变量所需栈空间过大超出栈限制。

### ※能介绍一下Golang中的map的扩容机制吗？

在Golang中，map的扩容机制主要由负载因子和溢出桶数量决定。当负载因子超过6.5时，会触发翻倍扩容，即桶的数量翻倍；当溢出桶的数量过多时，会触发等量扩容，即创建一个与旧桶数组数量 相同的新桶数组。

扩容过程是渐进式的，在每次对map进行插入、删除或查找操作时，会顺便搬迁一部分旧桶中的键值对到新桶中，直到所有旧桶中的键值对都被搬迁完毕。

引用传递：slice是引用类型，将其传递给函数或赋值给其他变量时，传递的是底层数据结构的副本，它们指向同一个底层数组，函数内部修改slice元素会影响原slice。

切片操作：可以通过s\[low:high\]的语法创建新的slice，新slice和原slice共享底层数组，修改新slice元素会影响原slice。

### 解释一下 Go hand off 机制 ？

在Go的GPM并发模型中，当一个M因为系统调用、阻塞操作等原因无法继续执行当前G时，调度器会将该M上的P转移到其他空闲的M上，或者创建一个新的M来接管这个P。

### 解释一下Go中的锁有哪些 ？

互斥锁（sync.Mutex）：同一时间只允许一个 goroutine 访问共享资源，用于保护对共享资源的写操作，避免数据不一致。

读写锁（sync.RWMutex）：允许多个 goroutine 同时进行读操作，但写操作会独占锁，适用于读多写少的场景。

条件变量（sync.Cond）：用于等待某个条件的发生，通常与互斥锁一起使用，适用于生产者 - 消费者模型。

原子操作（sync/atomic 包）：对基本数据类型进行原子性的读写操作，避免了锁的开销，适用于简单的计数器、标志位等场景。

### ※请说一说Golang的Http包的内存泄漏 ？

在Go语言（Golang）中，内存泄漏通常是指程序占用的内存未被及时释放，导致内存使用量不断增加，最终可能导致系统崩溃或性能下降。

Golang的net/http包提供了构建HTTP客户端和服务器的功能。它包含处理HTTP请求、响应、路由、中间件等功能，在Web开发中广泛使用。

常见的内存泄漏场景包括长时间持有请求上下文、未关闭响应体、goroutine泄漏和缓存未清理。未关闭响应体导致连接和相关资源无法释放；goroutine泄漏使goroutine一直占用内存和CPU资源；缓存未清理会使缓存不断增长。

### 请问Golang中的map的key为什么是无序的？

Golang中的map的key是无序的，原因主要有以下几点：一是其底层基于哈希表实现，哈希函数将键随机映射到数组的索引位置，决定了键值对在存储时没有特定顺序；二是Go语言设计者有意让map遍历顺序不确定，以避免开发者编写依赖map遍历顺序的代码，防止代码在不同环境下出现不一致行为；三是当map进行重新哈希操作时，键值对会重新映射到新的数组中，导致遍历顺序改变。所以，在使用map时不能依赖其键的遍历顺序。

### 请问在Golang中，函数返回局部变量的指针是否安全？

Go语言通过逃逸分析和垃圾回收机制，避免了悬空指针问题(即指针指向的内存已被释放)。Go编译器会分析变量的作用域，决定将其分配在栈还是堆上。堆上的变量由垃圾回收器管理，确保不会出现悬空指针。

### 闭包错误引用同一个变量问题如何处理 ？

在 Go 中，闭包会捕获其外部变量的引用，这可能导致在循环中创建多个闭包时，所有闭包都在引用同一个变量，从而造成意外的结果。

使用函数参数传递变量值：在循环内创建一个新的匿名函数，将当前循环变量的值作为参数传递给这个匿名函数，让闭包捕获参数的值。

在循环内创建局部变量：在循环内部创建一个新的局部变量，将循环变量的值赋给它，让闭包引用这个局部变量。

### 阐述一下 Go 的 select 底层数据结构和一些特性？

Go语言中select语句的底层数据结构主要包括scase和selectgo结构体。scase结构体代表一个case语句，包含通道指针、数据缓冲区和case类型等信息；selectgo结构体是select语句的核心，包含scase数组以及用于随机化、轮询和锁定通道的顺序数组。

select语句具有以下特性：多个case同时就绪时会随机选择一个执行，保证公平性；没有case就绪时会阻塞，直到有一个case准备好；若存在default分支，当没有case就绪时会立即执行default分支，不会阻塞；还可以结合time.After函数实现超时处理。

### 阐述一下Go 如何Array 类型的值作为函数参数 ？

在Go语言中，将Array类型的值作为函数参数时是按值传递的。函数接收的是数组的一个副本，对函数内部副本的修改不会影响到原始数组。例如，定义一个接收数组参数的函数，在函数内部对数组元素进行修改，原始数组不会发生改变。

### Golang协程比线程轻量主要体现在以下几个方面：

线程：线程是操作系统中的一个基本执行单元，它是程序执行的最小单位，它被包含在进程之中。。

协程：也叫轻量级线程，是一种用户态的轻量级线程，协程的调度完全由用户控制。

内存占用：线程的栈空间通常为几MB，而协程的栈空间初始只有几KB，且可动态伸缩，相同内存下能创建更多协程。

创建和销毁开销：线程的创建和销毁由操作系统内核负责，涉及用户态和内核态切换，开销大；协程由Go运行时在用户态管理，开销小。

调度开销：线程调度由操作系统内核进行，上下文切换开销大；协程调度在用户态进行，只需保存和恢复少量上下文信息，调度开销小。

并发能力：由于协程轻量，可创建大量协程实现高并发，而线程数量过多会导致系统性能下降。

### 阐述一下Go的select的运行原理 ？

Go 的 select 语句是用于处理多个通道（channel）操作的控制结构。它允许同时等待多个通道操作，使得 goroutine 在多个通信操作之间进行选择。

Go的select语句用于在多个channel操作上进行选择。其运行原理如下：首先，Go运行时会随机打乱所有case语句的顺序，然后依次检查每个case对应的channel操作是否可以立即执行。如果有一个或多个case就绪，Go运行时会随机选择一个执行；如果没有case就绪且有default语句，则执行default语句；若没有default语句，当前goroutine会被阻塞，直到有一个case就绪。

### 阐述一下Go的对象在内存中分配原理 ？

Go的对象在内存中的分配原理基于栈和堆两种内存区域，由编译器的逃逸分析决定具体的分配位置。

当对象的生命周期仅限于当前函数时，编译器会将其分配到栈上，栈分配速度快，由编译器自动管理，每个goroutine都有自己的栈。

当对象的指针被返回、传递给其他函数或者赋值给全局变量等，导致对象的生命周期超出当前函数时，编译器通过逃逸分析将其分配到堆上。堆上的对象由垃圾回收器管理，垃圾回收器会定期回收不再被引用的对象，避免内存泄漏。堆的空间较大。

**阐述一下Go语言的栈空间管理 ？**

每个goroutine都有独立的栈空间，创建时会分配一个初始的较小栈空间。栈采用连续内存块，栈指针指向栈顶，新栈帧从栈顶向下增长。

当栈空间不足时，Go运行时会自动进行栈空间增长，包括分配新栈、复制数据、更新指针和释放原栈等操作。函数返回时，栈空间会收缩，运行时还会定期检查并将空闲较多的栈空间收缩到合适大小。

栈空间分配和释放速度快，但栈空间增长和收缩操作有一定性能开销。

### ※线程模型有哪些？为什么 Go Scheduler 需要实现 M:N 的方案？Go Scheduler 由哪些元素构成呢？

线程模型主要有三种：1:1 模型（一个用户线程对应一个内核线程）、N:1 模型（多个用户线程映射到一个内核线程）和 M:N 模型（M 个用户线程映射到 N 个内核线程）。

### Channel同步、异步？阻塞、非阻塞？

在Go语言中，Channel既有同步的也有异步的。

无缓冲Channel是同步的，创建时不指定缓冲区大小，例如ch := make(chan int)。使用无缓冲Channel进行发送和接收操作时，发送操作会阻塞，直到有另一个goroutine从该Channel接收数据；接收操作也会阻塞，直到有另一个goroutine向该Channel发送数据，可用于两个goroutine之间的同步。

有缓冲Channel是异步的，创建时指定了缓冲区大小，例如ch := make(chan int, 2)。当向有缓冲Channel发送数据时，如果缓冲区未满，发送操作不会阻塞；从有缓冲Channel接收数据时，如果缓冲区不为空，接收操作也不会阻塞。只有当缓冲区满时发送操作才会阻塞，缓冲区为空时接收操作才会阻塞。可用于解耦生产者和消费者，提高并发性能。

阻塞机制：无缓冲的channel发送和接收操作是同步的，双方都必须准备好才能完成数据传递，否则会阻塞；有缓冲的channel只有在缓冲区满或空时才会阻塞。

数据传递：无缓冲的channel数据直接从发送方到接收方；有缓冲的channel数据先存于缓冲区，发送方和接收方不需要同时操作。

### TCP 的三次握手

目的：建立客户端与服务器之间的连接，确保双方都能发送和接收数据。

第一次握手：客户端发送 SYN（同步）报文，序列号为 x，进入 SYN_SENT 状态。

第二次握手：服务器收到 SYN 后，回复 SYN-ACK（同步-确认）报文，序列号为 y，确认号为 x+1，进入 SYN_RECEIVED 状态。

第三次握手：客户端收到 SYN-ACK 后，发送 ACK（确认）报文，序列号为 x+1，确认号为 y+1，进入 ESTABLISHED 状态。服务器收到 ACK 后也进入 ESTABLISHED 状态。

意义：确保双方都能正常发送和接收数据，避免无效连接。

第一次和第二次握手不可以携带数据，第三次握手可以携带数据。

### TCP 的四次挥手

目的：断开客户端与服务器之间的连接，确保数据完整传输。

第一次挥手：客户端发送 FIN（结束）报文，序列号为 u，进入 FIN_WAIT_1 状态。

第二次挥手：服务器收到 FIN 后，回复 ACK 报文，确认号为 u+1，进入 CLOSE_WAIT 状态。客户端收到 ACK 后进入 FIN_WAIT_2 状态。

第三次挥手：服务器发送 FIN 报文，序列号为 w，进入 LAST_ACK 状态。

第四次挥手：客户端收到 FIN 后，回复 ACK 报文，确认号为 w+1，进入 TIME_WAIT 状态。服务器收到 ACK 后关闭连接。客户端等待 2MSL（最大报文段生存时间）后关闭连接。

意义：确保双方都能正常关闭连接，避免数据丢失。

### 为什么需要三次握手，而不是两次？为什么要三次握手，而不是四次？

避免旧连接的初始化：防止已过期的连接请求报文突然又传送到服务器，因而产生错误和资源浪费。

建立可靠连接：三次握手双方可以确认对方的接收和发送能力。

同步初始序列号：确保双方能够正确地对数据进行排序和确认。

因为两次握手无法保证双方的发送和接收能力都正常，也不能有效避免旧连接的影响。

因为三次握手已经可以确认双方的发送接收能力正常，双方都知道彼此已经准备好，而且也可以完成对双方初始序号值得确认，也就无需再第四次握手了。

### 什么是 SYN洪泛攻击？如何防范？

SYN洪泛攻击属于 DOS 攻击的一种，它利用 TCP 协议缺陷，通过发送大量的半连接请求，耗费 CPU 和内存资源。

如果接收到客户端的 \[ACK\]，则 TCP 连接成功，如果未接受到，则会不断重发请求直至成功。SYN 攻击的攻击者在短时间内伪造大量不存在的 IP 地址，向服务器不断地发送 \[SYN\] 包，服务器回复 \[SYN/ACK\] 包，并等待客户的确认。由于源地址是不存在的，服务器需要不断的重发直至超时。

防范：

通过防火墙、路由器等过滤网关防护。

通过加固 TCP/IP 协议栈防范，如增加最大半连接数，缩短超时时间。

SYN cookies技术。SYN Cookies 是对 TCP 服务器端的三次握手做一些修改，专门用来防范 SYN 洪泛攻击的一种手段。

### 三次握手连接阶段，最后一次ACK包丢失，会发生什么？

如果ACK只是偶尔丢失，服务器会重发SYN-ACK，客户端再发ACK，最终连接仍能建立。

如果ACK持续丢失（如网络异常），服务器在多次重传SYN-ACK超时后，会关闭连接。

### 为什么连接的时候是三次握手，关闭的时候却是四次握手？

服务器在收到客户端的 FIN 报文段后，可能还有一些数据要传输，所以不能马上关闭连接，但是会做出应答，返回 ACK 报文段.

接下来可能会继续发送数据，在数据发送完后，服务器会向客户单发送 FIN 报文，表示数据已经发送完毕，请求关闭连接。

### 为什么客户端的 TIME-WAIT 状态必须等待 2MSL ？

确保 ACK 报文能够到达服务端，从而使服务端正常关闭连接。

防止已失效的连接请求报文段出现在之后的连接中。等待 2MSL，可以确保旧连接的所有数据包都已超时消失，避免影响新连接。

### 如果已经建立了连接，但是客户端出现故障了怎么办？

TCP 设有一个保活计时器。服务器每收到一次客户端的数据，都会重新复位这个计时器，通过定时器 + 超时重试机制，尝试获取确认，直到最后会自动断开连接。

### TIME_WAIT 是服务器端的状态?还是客户端的状态?

TIME_WAIT 是主动断开连接的一方会进入的状态，一般情况下，都是客户端所处的状态;服务器端一般设置不主动关闭连接。

TIME_WAIT 需要等待 2MSL，在大量短连接的情况下，TIME_WAIT会太多，这也会消耗很多系统资源。对于服务器来说，在 HTTP 协议里指定 KeepAlive（浏览器重用一个 TCP 连接来处理多个 HTTP 请求），由浏览器来主动断开连接，可以一定程度上减少服务器的这个问题。

### 详细讲一下TCP的滑动窗口？

在进行数据传输时，如果传输的数据比较大，就需要拆分为多个数据包进行发送。TCP 协议需要对数据进行确认后，才可以发送下一个数据包。这样一来，就会在等待确认应答包环节浪费时间。

窗口大小指的是不需要等待确认应答包而可以继续发送数据包的最大值。滑动窗口一块是已经发送但是未被确认的分组，另一块是窗口内等待发送的分组。随着已发送的分组不断被确认，窗口内等待发送的分组也会不断被发送，让还没轮到的分组进入窗口内。

### 什么是 Cookie?

Cookie是Web服务器发送到用户浏览器并保存在本地的小段数据，用于在客户端和服务器之间传递信息。其工作原理是服务器在响应头中通过Set - Cookie字段设置Cookie，浏览器保存后在后续请求的请求头Cookie字段中携带。

Cookie的作用主要包括会话管理、个性化设置和统计分析等。它分为会话Cookie和持久Cookie，会话Cookie保存在浏览器内存，关闭浏览器即删除；持久Cookie有明确过期时间，保存在硬盘。

### 什么是HTTP协议？

HTTP（超文本传输协议）是用于在互联网上传输超文本的应用层协议，客户端和服务器通过请求和响应进行通信，它基于请求 - 响应模式工作。客户端向服务器发送HTTP请求，服务器处理后返回HTTP响应。

HTTP协议具有无状态、简单快速、灵活、无连接等特点。无状态意味着每个请求都是独立的，服务器不保留之前请求的状态；简单快速使得协议易于实现和解析；灵活体现在可以传输多种类型的数据；无连接是指每次请求 - 响应完成后连接会关闭。

HTTP的安全版本是HTTPS（超文本传输安全协议），通过SSL/TLS加密数据传输，确保数据的安全性和完整性。

### 什么是HTTP状态码？举例说明几个常见的HTTP状态码及其含义。

HTTP状态码是服务器响应客户端请求时返回的三位数字代码，它们用于表示请求的处理结果。状态码由三部分构成：第一位数字表示响应分类，后两位数字提供更具体的状态信息。

200 OK：请求成功，服务器已成功处理请求。

301 Moved Permanently：请求的资源已永久移动到新的URL。

400 Bad Request：客户端请求有语法错误，不能被服务器识别。

404 Not Found：请求的资源不存在。

500 Internal Server Error：服务器内部发生错误，无法完成请求。

1xx（信息性状态码）：表示请求已被接收，需要继续处理。

2xx（成功状态码）：表示请求已成功被服务器接收、理解并处理。

3xx（重定向状态码）：表示需要客户端采取进一步的操作才能完成请求，通常用于重定向。

4xx（客户端错误状态码）：表示客户端可能存在错误，导致请求无法被服务器处理。

5xx（服务器错误状态码）：表示服务器在处理请求时发生了错误。

### ※请解释一下DNS是什么以及它的作用是什么？UDP 53

DNS即域名系统（Domain Name System），是一个将域名和IP地址相互映射的分布式数据库，主要用于将人类易于记忆的域名（如 www.example.com）转换为计算机能够理解的IP地址（如 192.0.2.1）。这个过程称为域名解析。

其主要作用包括：将用户输入的域名解析为对应的IP地址，使计算机能够找到目标服务器并建立连接；支持反向解析，将IP地址转换为域名；通过一定策略实现负载均衡，把不同用户的域名解析请求指向不同服务器；采用分布式架构，确保系统具有高可用性和可扩展性。

DNS的工作原理：

查询：当用户在浏览器中输入域名时，系统首先会检查本地缓存是否有对应的IP地址。

递归查询：如果缓存中没有，计算机会向配置的DNS服务器发送查询请求。

根服务器：DNS服务器可能首先向根DNS服务器查询，以获取顶级域名服务器的信息。

顶级域名服务器：然后DNS服务器查询相应的顶级域名服务器（如.com、.org等），获得所查询域名的权威DNS服务器的地址。

权威DNS服务器：最终，查询权威DNS服务器，以获取该域名对应的IP地址。

返回响应：DNS服务器将IP地址返回给请求的计算机，并在本地缓存中存储该信息，以便将来快速访问。

### HTTP 1.0 和 HTTP 1.1 之间有哪些区别？

连接管理：HTTP 1.0默认是非持久连接，每次请求都要建立和关闭TCP连接；HTTP 1.1默认是持久连接，一个TCP连接可处理多个请求响应，减少了连接开销。

请求方法：HTTP 1.0主要支持GET、POST和HEAD；HTTP 1.1增加了PUT、DELETE、OPTIONS、TRACE等方法。

状态码：HTTP 1.1新增了100、303、307等状态码，用于更精确的响应和重定向处理。

请求头字段：HTTP 1.1引入了Host字段，适用于虚拟主机环境；还引入了更多缓存控制字段。

分块传输编码：HTTP 1.1支持分块传输编码，允许服务器在不确定响应长度时将数据分块传输。

缓存机制：HTTP 1.1对缓存机制进行了改进，引入Cache - Control和ETag等字段进行更精细的缓存控制。

### HTTP 和 HTTPS 的区别？

在安全性上，HTTP是明文传输，易被截取和篡改；HTTPS通过SSL/TLS协议加密并进行身份验证，能有效防止信息泄露和中间人攻击。

端口号方面，HTTP默认使用80端口，HTTPS默认使用443端口。

协议结构上，HTTP结构简单，HTTPS在HTTP基础上增加了SSL/TLS握手过程。

性能上，HTTP速度快、资源消耗小，HTTPS因加密操作速度慢、消耗资源多。

部署成本上，HTTP部署简单成本低，HTTPS需购买证书且配置复杂，成本较高。

SSL/TLS协议是一种用于在网络通信中提供加密和身份验证的协议，它主要包括握手阶段和数据传输阶段。

### HTTPS 大概过程流程讲一下？

客户端发起请求，向服务器发送自己支持的SSL/TLS版本和加密算法列表等信息。

服务器响应，选择一个SSL/TLS版本和加密算法，并将自己的证书（包含公钥）发送给客户端。

客户端验证证书的有效性，若验证通过则提取服务器的公钥。

客户端生成一个随机的会话密钥，使用服务器的公钥对其进行加密后发送给服务器。

服务器使用自己的私钥解密得到会话密钥。

双方发送确认消息完成握手，之后使用会话密钥进行对称加密通信。

在数据传输阶段，客户端和服务器使用会话密钥对数据进行加密和解密。

数据传输完成后，关闭SSL/TLS连接。

### OSI七层模型

物理层负责传输比特流，定义了物理介质（如电缆、光纤）、信号的传输方式（如电压、光强度）。

数据链路层将物理层接收到的比特流封装成帧，进行差错检测和纠正，同时负责MAC地址的寻址。常见协议：以太网协议（Ethernet）、点对点协议（PPP）等。

网络层负责将数据包从源节点传输到目标节点，进行路由选择和寻址，使用IP地址。常见设备：路由器。常见协议：IP协议（IPv4、IPv6）、ICMP协议等。

传输层提供端到端的可靠或不可靠传输服务，主要协议有TCP和UDP。TCP提供面向连接的、可靠的传输，UDP提供无连接的、不可靠的传输。

会话层建立、管理和终止不同主机上应用程序之间的会话，包括会话的建立、拆除和同步。常见协议：NetBIOS、RPC（远程过程调用）等。

表示层处理数据的表示和转换，如加密、解密、压缩、解压缩等，确保不同系统之间能够正确理解数据。

应用层为用户的应用程序提供网络服务，如文件传输、电子邮件、网页浏览等。

### TCP 和 UDP的概念及特点

TCP（Transmission Control Protocol）即传输控制协议，是一种面向连接的、可靠的、基于字节流的传输层通信协议。在进行数据传输前，需要通过“三次握手”建立连接，传输完成后，通过“四次挥手”断开连接。适用场景：如文件传输、网页浏览等，这些场景对数据的准确性要求较高。可靠、面向连接、字节流传输、拥塞控制

UDP（User Datagram Protocol）即用户数据报协议，是一种无连接的传输层协议，提供面向事务的简单不可靠信息传送服务。直接将数据报发送到目标地址。UDP适用场景：如视频会议、实时游戏等，这些场景对实时性要求较高。无连接、不可靠、数据报传输、没有拥塞控制。

### 什么是IP地址？IPv4和IPv6有什么区别？

IP地址是一个用于标识网络中设备的逻辑地址。它可以看作是互联网上每个设备的“邮寄地址”，通过这个地址，数据包可以在网络中找到发送和接收的目标。

IPv4和IPv6的区别主要体现在以下几个方面：

地址长度：IPv4是32位，地址资源有限；IPv6是128位，能提供近乎无限的地址。

表示形式：IPv4采用点分十进制，IPv6采用冒号十六进制。

报头格式：IPv4报头可变长，格式复杂；IPv6报头固定为40字节，更简洁高效。

安全性：IPv4需依赖外部安全技术，IPv6集成了IPsec，有更好的安全性。

网络层协议：IPv4：在网络层的功能相对简单，主要用于数据传输(广播)。IPv6：提供了更复杂的功能，如多播（multicast）、任何播（anycast）等，适用于更复杂的网络通信需求。

配置与维护：

IPv4：支持手动配置和动态主机配置协议（DHCP），但管理相对较复杂。IPv6：支持更高级的自动配置功能（如无状态地址自动配置），使得网络配置和管理更加简便。

### ※什么是阻塞和非阻塞，同步和异步 前者指操作，后者指操作完成

同步异步强调的是两个操作之间的顺序关系，两个操作之间是有序的还是无序的；

阻塞与非阻塞强调的是一个调用发起后调用发起方的行为，是被动等待还是主动获得执行权；

同步指的是某个操作 A 必须等待前一个操作 B 完成之后才能开始，也就是说 A 在 B 完成之前不会启动。先穿袜子再穿鞋

在异步操作中，操作 A 不需要等待前一个操作 B 完成之后才能开始，A 和 B 可以同时进行，或者 A 可以在等待 B 的过程中执行其他操作。

阻塞调用发出后，调用方会挂起等待，当被调用方执行完成并返回结果后，调用方才会被唤醒并接到结果继续执行之后的操作。说白了阻塞调用就是发出调用后傻等着，整个进程都等在调用发出这一行。

非阻塞调用发出后，调用方不会挂起等待，而是立即返回，之后可以选择继续别的操作。被调用方在后台(可能以各种形式实现)处理原本的业务逻辑，处理完成后可以通过回调、信号等机制通知调用方。说白了非阻塞调用就是发出调用后马上返回，无论能不能得到想要结果都义无反顾的返回

阻塞是指程序在执行I/O操作时，如果操作不能立即完成，会暂停执行，进入等待状态，直到操作完成才继续后续代码。非阻塞则是程序执行I/O操作时，若操作不能立即完成会立即返回，程序可继续执行其他任务，后续再检查操作状态。

同步是程序发起I/O请求后，需主动等待操作完成并获取结果，期间程序控制权被占用。异步是程序发起I/O请求后，无需等待操作完成，可继续执行其他任务，操作完成后系统会通过回调等方式通知程序。

### 在浏览器中输入 URL 地址到显示主页的过程？

解析URL，浏览器生成http请求，

首先进行DNS解析获取域名对应的IP地址。接着，浏览器与该IP地址通过三次握手建立TCP连接。然后，浏览器通过已建立的TCP连接向服务器发送HTTP请求。服务器接收到请求后，对其进行解析并处理，生成HTTP响应。浏览器接收服务器返回的HTTP响应，开始解析渲染页面。最后，浏览器和服务器之间的TCP连接通过四次挥手关闭。

### ※解释一下HTTPS，以及它与HTTP的区别是什么？ 安端证能L

HTTPS在HTTP的基础上增加了一层安全性，通过使用SSL（Secure Sockets Layer）或TLS（Transport Layer Security）加密协议来保障数据的安全传输。客户端和服务器在通信前会进行SSL/TLS握手，协商加密算法和生成会话密钥，之后使用会话密钥对数据进行加密传输。

客户端向服务器发送HTTP请求、ClientHello消息，请求中包含客户端支持的SSL/TLS版本和加密算法等信息。

服务器接收到请求后，选择一个SSL/TLS版本和加密算法，并返回ServerHello消息和数字证书。

客户端验证服务器证书的有效性，如果有效，则生成一个会话密钥，并使用服务器证书中的公钥对会话密钥进行加密后发送给服务器。

服务器使用自己的私钥解密会话密钥，然后双方使用会话密钥进行加密通信。

在会话结束阶段，客户端和服务器发送CloseNotify消息，关闭SSL/TLS连接。

HTTPS与HTTP的区别主要体现在以下几个方面：

安全性：HTTP是明文传输，易被窃听和篡改；HTTPS通过加密和身份验证确保数据安全。

端口：HTTP默认使用80端口，HTTPS默认使用443端口。

证书：HTTP不需要证书，HTTPS需要使用SSL/TLS证书来验证服务器身份。

性能：HTTP性能相对较高，HTTPS由于加密和解密操作以及SSL/TLS握手，会有一定的性能损耗。

URL形式：HTTP: 网址以http://开头。HTTPS: 网址以https://开头。

### ※说一说POST与GET有哪些区别 位置、大小、安、缓、幂

数据传输位置：GET请求的数据附加在URL后，POST请求的数据放在HTTP请求体中。

数据传输大小限制：GET受URL长度限制，传输数据量有限；POST无明显数据大小限制。

安全性：GET安全性较低，数据暴露在URL中；POST相对安全，但也需额外安全措施。

缓存：GET请求会被浏览器缓存，POST默认不缓存。

幂等性：GET是幂等的，多次请求结果相同；POST不是幂等的，多次请求可能产生不同影响。

使用场景：GET适用于获取数据，POST适用于提交数据。

### 请描述一下TCP/IP协议栈，并解释其中的每一层的作用。

网络接口层：负责将数据帧在物理网络上进行传输，处理与物理网络的接口细节。

网络层：主要负责数据包的路由和转发，根据目标IP地址选择合适的路径传输数据包。

传输层：提供端到端的可靠通信，将上层数据进行分段，并添加端口信息。常见协议有TCP和UDP。

应用层：为用户应用程序提供网络服务，定义了各种应用程序之间的通信规则和协议。

### ARP 协议的工作原理？

ARP（Address Resolution Protocol）即地址解析协议，用于将IP地址解析为对应的MAC地址。在以太网中，数据帧的传输依赖MAC地址，但上层网络应用通常使用IP地址来标识目标设备。IP地址是网络层的地址，用于在网络中标识不同的主机；MAC地址是数据链路层的地址，用于在同一局域网内唯一标识网络设备的网络接口。

IP地址可以比作为地址，MAC地址为收件人.

ARP（地址解析协议）的工作原理是用于将IP地址解析为对应的MAC地址。当一台主机需要向同一局域网内的另一台主机发送数据，且其ARP缓存表中没有目标主机的IP - MAC映射信息时，会构造一个ARP请求数据包并广播到局域网中。该请求包含源主机的IP地址和MAC地址以及目标主机的IP地址。

局域网内所有主机都会收到这个请求，但只有目标主机发现请求中的目标IP地址与自己的IP地址匹配时，才会构造一个包含自身IP地址和MAC地址的ARP响应数据包，并单播给源主机。源主机收到响应后，会将目标主机的IP - MAC映射信息添加到自己的ARP缓存表中，以便后续通信使用。

IP地址和MAC地址的区别和联系：

IP地址是逻辑地址，用于在网络层标识网络和主机，全球范围内唯一标识设备。

MAC地址是物理地址，用于在数据链路层标识网络接口设备，局域网内唯一标识设备。

IP地址长度为32位，MAC地址长度为48位。

寻址协议层不同，IP地址应用于OSI第三层，即网络层，而MAC地址应用在OSI第二层，即数据链路层。

### ※cookie和session是怎么实现用户的登录状态的？

Cookie 是服务器在用户的浏览器上保存的小数据片段，通常用于存储用户的偏好设置、登录信息等。

session是服务器端的会话机制，用于跟踪用户的会话状态。服务器会为每个会话分配一个唯一的ID，通过这个ID来识别不同的用户会话。

对于cookie，用户登录验证通过后，服务器生成包含登录状态信息的cookie并通过响应头的Set - Cookie字段发送给浏览器。浏览器保存该cookie，后续请求时会在请求头的Cookie字段中携带，服务器解析该字段来判断用户登录状态。

对于session，用户登录验证通过后，服务器创建session对象并分配唯一的session ID，将其以cookie形式发送给浏览器。后续请求中浏览器携带session ID，服务器根据该ID从session存储中查找对应session对象，以此判断用户登录状态。

需要注意的是，cookie存储在客户端，适合存储简单信息；session存储在服务器端，可存储更复杂的会话信息。

### HTTP 和 HTTP 2.0 的区别 分帧格式、多个请求、压缩头部、主动响应

在传输格式上，HTTP 1.1基于文本传输，解析处理复杂；HTTP 2.0采用二进制分帧，更高效可靠。

在连接处理方面，HTTP 1.1存在队头阻塞问题，同一时间一个TCP连接只能处理一个请求；HTTP 2.0通过多路复用机制，可在一个TCP连接上同时处理多个请求和响应。

头部处理上，HTTP 1.1头部信息重复发送浪费带宽；HTTP 2.0使用HPACK算法压缩头部，减少传输量。

服务器交互方面，HTTP 1.1客户端主动请求，服务器被动响应；HTTP 2.0支持服务器推送，可主动推送资源。此外，HTTP 2.0还支持为请求设置优先级。

### ※HTTP 长连接短连接使用场景是什么

HTTP短连接：每次HTTP请求都要建立新的TCP连接，请求完成后就关闭连接。

长连接（HTTP/1.1 默认）在一个 TCP 连接中，可以发送多个 HTTP 请求和响应，连接保持开放，直到一方显式关闭。

HTTP短连接适用于请求频率低、客户端资源有限以及对安全性要求高的场景。例如小型企业官网的静态页面访问、低功耗嵌入式设备的请求以及银行关键业务接口等。

HTTP长连接适用于频繁请求、数据交互量大以及服务器资源充足的场景。比如实时数据更新的页面、在线视频播放、在线游戏等。

### HTTPS 是如何保证通信安全的？

HTTPS通过SSL/TLS协议保证通信安全。在SSL/TLS握手阶段，客户端和服务器首先进行信息交换，服务器发送数字证书。客户端验证证书的有效性，提取服务器公钥。客户端生成随机数并用公钥加密后发送给服务器，双方据此生成会话密钥。

在这个过程中，结合了对称加密和非对称加密。非对称加密用于安全地交换会话密钥（客户端通过公钥来加密会话密钥，服务端通过私钥来解开会话密钥，至此会话密钥生成，连接成功），而对称加密用于后续通信阶段（两端通过会话密钥进行加密解密），提高数据加密和解密的效率。数字证书由权威CA颁发，用于证明服务器的身份和公钥的有效性，防止中间人伪造服务器身份。

### ※HTTP协议的优点和缺点

简单快速，请求和响应格式简单，能快速处理请求；采用无连接方式，节省传输时间，适合高并发场景；是无状态协议，减轻服务器存储压力；支持多种数据格式；可扩展。

明文传输不安全、缺乏实时性、无状态存储不了用户信息等

DNS同时使用TCP和UDP协议？

DNS同时使用TCP和UDP协议。在大多数日常的域名解析查询中，由于查询和响应的数据量较小，DNS使用UDP协议，因为UDP开销小、传输速度快，能快速完成解析请求。然而，当DNS查询或响应的数据量超过UDP数据包的最大长度，例如进行区域传输时，DNS会使用TCP协议，因为TCP协议能够保证可靠的数据传输和支持更大的数据量，确保大量数据准确无误地传输。

### 数据库的三大范式是什么

第一范式：保证每列的原子性，数据表中的所有字段值都是不可分解的原子值

第二范式：第二范式要求每个非主属性完全依赖于主键，不能只依赖主键的一部分。

第三范式：第三范式要求非主属性之间不能有传递依赖，也就是说，一个非主属性不能依赖于另一个非主属性。

### ※索引

索引是对数据库表的一列或者多列的值进行排序的一种结构，使用索引可以快速访问数据库表中的特定信息。包含主键索引、普通索引、唯一索引、全文索引等。

当在数据库表上创建索引时，数据库会为索引列的值构建一个数据结构，当执行查询时，数据库首先在索引中查找符合条件的值，根据索引中记录的物理地址直接定位到数据表中的相应记录，从而减少了磁盘I/O操作和数据扫描量。

优点：1.提高查询效率，减少全量数据扫描2.加速排序操作，利用索引的有序性直接完成排序3.优化连接操作，在连接列上创建索引能提高多表连接的效率4.保证数据的唯一性

缺点：占用额外空间：索引本身需要占用磁盘空间来存储索引数据结构。

降低数据写入、更新和删除的性能：因为在进行这些操作时，不仅要修改数据表中的数据，还要同时更新索引。

经常需要作为条件查询的列上适合创建索引，区分度低的一般不适合。

Mysql为什么不需要跳表：跳表的搜索操作从最顶层开始，逐层向下搜索目标元素，直至找到目标元素或者到达最底层。

B+树的高度在3层时存储的数据可能已达千万级别（2000w），但对于跳表而言，同样去维护千万的数据量会导致跳表层数过高，从而增加磁盘 I/O 次数。也就是说在存储相同的数据时，使用 B+树的磁盘 I/O 次数更少。

### 索引的数据结构?

B树：B 树是一种多路平衡搜索树，每个节点可以有多个子节点，所有叶子节点都在同一层。每个节点存储着键值和指向子节点的指针，也存放数据。

B+树：B+ 树是 B 树的一种变形，它的非叶子节点只存储键值和指向子节点的指针，不存储数据，所有数据都存储在叶子节点中，叶子节点之间通过指针相连。非叶子节点用双向链表连接。

哈希索引是基于哈希表实现的，对索引列计算哈希值把记录映射到哈希槽中，然后指向对应记录行的地址。

哈希表不支持排序，一般多用于精准的等值查找，存在哈希冲突，性能不稳定，B+树支持范围查询，模糊查询和多列索引最左前缀优先匹配，性能是相对稳定的，每次查询都是从根节点到叶子节点。

### 聚簇索引和非聚簇索引(二级索引，常用于非主键) 按照存储方式不同

聚集索引（聚簇索引）：以 InnoDB 作为存储引擎的表，表中的数据都会有一个主键，即使你不创建主键，系统也会帮你创建一个隐式的主键。~~这是因为 InnoDB 是把数据存放在 B+ 树中的，而 B+ 树的键值就是主键，在 B+ 树的叶子节点中，存储了表中所有的数据.~~这种以主键作为 B+ 树索引的键值而构建的B+树索引，我们称之为聚集索引。聚集索引的叶子节点存储的是实际的数据行。由于数据的物理存储顺序与索引顺序一致，所以对于范围查询和排序操作非常高效。

以主键以外的列值作为键值构建的 B+ 树索引，我们称之为非聚集索引。非聚集索引与聚集索引的区别在于非聚集索引的叶子节点不存储表中的数据，而是存储该列对应的主键，想要查找数据我们还需要根据主键再去聚集索引中进行查找，这个再根据聚集索引查找数据的过程，我们称为回表。索引覆盖：只需要在一棵索引树上就能获取SQL所需的所有列数据，无需回表，速度更快。如果一个索引包含所有需要查询的字段的值，称之为“覆盖索引”。

数据存储：聚簇索引里的数据行是按索引键值的顺序存储的，也就是说，索引的叶子节点里包含了实际的数据行。而在非聚簇索引中，叶子节点有指向数据行的指针和主键值。数据行其实存储在聚簇索引里。非叶子节点存放索引值。

前缀索引：在对字符串创建索引, 如INDEX(name)中, 若字符串非常大, 那么相应的空间使用和维护开销也非常大, 就可以使用字符串从左开始的部分字符创建索引（把很长字段的前面的公共部分作为一个索引，就会产生超级加倍的效果）, 减少空间和维护的成本, 但是也会降低索引的选择性。 最左前缀原则 就是利用索引列中最左的字段优先进行匹配。最左前缀原则就是最左优先，在创建多列索引时，要根据业务需求，where子句中使用最频繁的一列放在最左边。 mysql会一直向右匹配直到遇到范围查询(>、<、between、like)就停止匹配。

如果聚簇索引的数据更新，它的存储要不要变化？

如果更新的数据是非索引数据，也就是普通的用户记录，那么存储结构是不会发生变化。

如果更新的数据是索引数据，那么存储结构是有变化的，因为需要维护 b+ 树的有序性。

### 为什么官方建议使用自增长主键作为索引？

结合B+Tree的特点，自增主键是连续的，在插入过程中尽量减少页分裂，即使要进行页分裂，也只会分裂很少一部分。并且能减少数据的移动，每次插入都是插入到最后。总之就是减少分裂和移动的频率。因为索引是有序存放的，否则要进行复杂的移动等操作

### 什么情况下索引会失效？即查询不走索引？

对索引列进行函数操作，因为函数改变了索引列的原始值，无法直接利用索引结构。

使用隐式类型转换，查询条件的数据类型与索引列不一致，会使MySQL进行隐式转换，从而无法使用索引。

使用OR连接条件，且部分条件无索引，可能导致全表扫描。

复合索引中，前面列使用范围查询，后面列索引失效。

模糊查询以通配符%开头，无法从索引开头定位匹配数据。

统计数据不准确，优化器可能做出错误决策不使用索引。

### 介绍一下MySQL主从架构？

MySQL主从架构是一种将数据从一个MySQL数据库（主库，Master）复制到其他多个MySQL数据库（从库，Slave）的架构模式。主库负责处理写操作（如插入、更新、删除），从库负责处理读操作，实现读写分离，提高数据库的并发处理能力。其工作流程是主库将写操作记录到二进制日志，从库通过IO线程接收主库的二进制日志并保存到中继日志，再由SQL线程执行中继日志中的SQL语句实现数据同步。

主从架构具有读写分离、数据备份、负载均衡和高可用性等优势。不过，主从架构可能面临数据延迟、主从数据不一致和主库故障等问题，可通过优化网络、定期检查数据一致性和使用自动化故障切换工具来解决。

### ※实践中如何优化MySQL

索引优化：在经常用于查询条件、连接条件和排序的列上合理创建索引，避免过多索引，使用复合索引提高查询效率。

查询优化：避免全表扫描，优化子查询，减少不必要的列查询，使用 EXPLAIN 分析查询语句的执行计划。

配置优化：合理调整 MySQL 的内存、线程、日志等配置参数，根据服务器的硬件资源和业务需求进行优化。

表结构优化：选择合适的数据类型，合理设计表的范式，对于大型表可以使用分区表。

硬件优化：使用高性能磁盘、增加内存、升级 CPU 等，提高服务器的硬件性能。

### 简单描述mysql中，索引，主键，唯一索引，联合索引的区别，对数据库的性能有什么影响（从读写两方面）

在MySQL中，索引是提高查询效率的数据结构，普通索引不限制值的唯一性；主键是特殊的唯一索引，能唯一标识表中的每一行，且值不能为NULL；唯一索引要求索引列的值唯一，允许有一个NULL值；联合索引是基于多个列创建的索引，遵循最左前缀原则。

由于InnoDB的聚簇索引特性，主键查询通常是最快的，因为数据按照主键顺序存储，查询时可以直接定位到数据页。

在性能方面，读操作时，各类索引都能提高查询效率，但主键查询通常最快，联合索引需符合最左前缀原则才能发挥作用。写操作时，索引会增加开销，列数越多的联合索引和需要检查唯一性的唯一索引开销更大，主键如果不是顺序插入也可能影响性能。在设计数据库时，应根据实际业务需求合理使用索引，避免过度索引。

### 索引的三种常见底层数据结构以及优缺点

B 树是一种多路平衡搜索树，优点是查询效率高、支持范围查询、插入和删除操作相对高效；缺点是占用存储空间大，磁盘 I/O 效率较低。

B+ 树是 B 树的变形，非叶子节点不存储数据，所有数据都在叶子节点且叶子节点相连。优点是适合磁盘存储、范围查询效率高、查询稳定性好；缺点是插入和删除操作复杂，部分查询也需遍历到叶子节点。

哈希表通过哈希函数映射键值，优点是查找速度极快、实现简单；缺点是不支持范围查询、哈希冲突会影响性能、维护有额外开销。

持久化: Redis 提供了持久化机制，可以将内存中的数据定期保存到磁盘，防止系统崩溃时数据丢失。它支持两种持久化方式：

RDB（快照）：RDB持久化是将Redis在某个时间点上的数据集快照保存到磁盘上，生成一个二进制文件。适合对大规模的数据恢复，比AOF的启动效率高；数据安全性低，如果Redis突然宕机，会丢失最后一次快照修改。h持久化实际操作过程是fork一个子进程，先将数据集写入临时文件，写入成功后，再替换之前的文件，用二进制压缩存储

AOF（追加文件）：AOF持久化是将Redis执行的每个写命令追加到一个日志文件（通常是appendonly.aof）中。当Redis重启时，会重新执行这些命令来恢复数据。记录每次写操作，支持更高的数据安全性。对于相同数量的数据集而言，AOF文件通常要大于RDB文件；AOF在运行效率往往要慢于RDB。(太大了就重写)

### ※Redis是单线程还是多线程？Redis为什么这么快？

6.0之前使用单：单线程的Redis的瓶颈通常在CPU的IO，而在使用Redis时几乎不存在CPU成为瓶颈的情况。使用Redis主要的瓶颈在内存和网络。因为Redis是基于内存的操作，CPU不是Redis的瓶颈，Redis的瓶颈最有可能是机器内存的大小或者网络带宽。既然单线程容易实现，而且CPU不会成为瓶颈

为什么这么快主要有以下几个原因

运行在内存中数据结构简单、使用多路IO复用技术、单线程实现，单线程避免了线程切换、锁造成的性能开销

为什么6.0后改为多线程？

Redis的瓶颈在内存和网路，Redis6.0引入多线程主要是为了解决网络IO读写瓶颈，将主线程 IO 读写任务拆分出来给一组独立的线程处理，使得多个 socket 读写可以并行化，执行命令还是单线程执行

zset跳跃表（面试常问）：跳跃表是一种有序数据结构，它通过在每个节点维持多个指向其他结点的指针，从而达到快速访问节点的目的。跳跃表是有序集合键的底层实现之一，跳跃表在原有的有序链表上增加了多级索引，通过索引来实现快速查询。

### 键的过期删除策略

惰性删除：只有访问这个键时才会检查他是否过期，如果过期则删除。优点：最大化地节约CPU资源。缺点：如果大量过期键没有被访问，会一直占用大量内存

定时删除：为每一个设置唾弃时间的key都创造一个定时器，到了过期时间就清除。优点：该策略可以立即清除过期的键。缺点：会占用大量CPU资源去处理过期的数据

定期删除：每隔一段时间就对一些键进行检查，删除其中过期的键。该策略时惰性删除和定时删除的一个折中，既避免了占用大量CPU资源又避免了出现大量过期键不被清除占用内存的情况

Redis中同时使用了惰性删除和定期删除两种

给单个key设置过期时间；惰性删除：当客户端访问某个key就检查；定期删除：周期性随机取一些设置了过期时间的key检查；还可能通过内存淘汰策略，清除key

### RDB，AOF都开启时，服务器是如何加载数据的，数据以谁为准？

服务器启动时会优先检查AOF文件是否存在。如果AOF文件存在，服务器会加载AOF文件来恢复数据；只有当AOF文件不存在时，服务器才会加载RDB文件。在这种情况下，数据以AOF文件为准。因为AOF文件通过记录所有写命令来保证数据的最新状态，能反映出从上次RDB快照生成之后的所有数据更新，而RDB文件只是某个时间点的快照。

### 谈一谈你对Redis事务的理解？

事务是一组命令的集合，这组命令要么全部执行成功，要么全部不执行，以保证数据的一致性和完整性。

一致性：从A状态经过事务转移到B状态，并不会破坏各种约束。

Redis事务不保证原子性，单条的Redis命令是原子性的，但事务不能保证原子性，而Redis的一致性是要么都运行，要么都不运行，所以不存在一致性。

Redis事务是有隔离性的，但是没有隔离级别，Redis是单线程执行命令的，这保证了在同一时间只有一个命令在执行，事务中所有命令都会序列化、按顺序地执行。事务在执行的过程中，不会被其他客户端发送过来的命令请求所打断（顺序性、排他性）

持久性：Redis事务的持久性取决于Redis的持久化策略。

Redis事务不支持回滚 ，Redis执行过程中的命令执行失败，其他命令仍然可以执行

原因：Redis命令简单(只有两种错误：语法错误、要执行的key数据类型不匹配)，Redis内部实现简单高效

Redis事务的执行流程包括使用MULTI开启事务，将命令依次入队，使用EXEC执行事务队列中的命令，也可以使用DISCARD取消事务。错误处理分为语法错误和运行时错误，语法错误会导致整个事务不执行，运行时错误只会使该命令执行失败，不影响后续命令。

Redis事务为什么不支持回滚？

Redis命令简单，只在两种情况失败：语法错误的时候才失败（在命令输入的时候不检查语法）；要执行的key数据类型不匹配：这种错误实际上是编程错误，这应该在开发阶段被测试出来，而不是在生产上

因为不需要回滚，所以Redis内部实现简单并高效。

### Redis集群介绍一下

如果数据量很少，主要是承载高并发高性能的场景，比如缓存一般就几个G的话，单机足够了。 主从模式：master 节点挂掉后，需要手动指定新的 master，可用性不高，基本不用。 哨兵模式：master 节点挂掉后，哨兵进程会主动选举新的 master，可用性高，但是每个节点存储的数据是一样的，浪费内存空间。数据量不是很多，集群规模不是很大，需要自动容错容灾的时候使用。 Redis cluster 主要是针对海量数据+高并发+高可用的场景，如果是海量数据，如果你的数据量很大，那么建议就用Redis cluster，所有master的容量总和就是Redis cluster可缓存的数据容量。

为什么使用集群：单机Redis存在容量和性能瓶颈，当数据量增大或并发请求增多时，单机无法满足需求。单机Redis存在单点故障问题，一旦服务器出现故障，整个服务会中断。分布式系统是将多个计算机节点连接在一起，共同完成一个任务的系统。

Redis集群是一个分布式的Redis实现，它通过分片的方式将数据分布在多个节点上，每个节点负责存储部分数据。它具有数据分片、高可用性、自动故障转移和水平扩展等特点。

数据分片：Redis集群将整个键空间划分为16384个槽（slot），每个节点负责一部分槽的数据存储。

高可用性：Redis集群采用主从复制和故障转移机制，当主节点出现故障时，从节点可以自动晋升为主节点，保证系统的可用性。

自动故障转移：Redis集群通过哨兵（Sentinel）或集群内部的故障检测机制来检测节点的状态，当发现节点故障时，会自动进行故障转移。

主从复制：每个主节点都可以有多个从节点，从节点会复制主节点的数据，当主节点出现故障时，从节点可以晋升为主节点。

水平扩展：可以通过添加或删除节点来动态调整集群的容量和性能。

Redis集群适用于大数据量存储、高并发访问等场景。

### 主从模式

主从模式：Redis单机版通过RDB或AOF持久化机制到硬盘上，但数据都存储在一台服务器上，并且读写都在同一服务器上（读写不分离），如果硬盘出现问题，则会导致数据不可用，为了避免这种问题，Redis提供了复制功能，在master数据库中的数据更新后，自动将更新的数据同步到slave数据库中，这就是主从模式的Redis集群。

数据同步方式有全量同步和增量同步。新从节点连接主节点时进行全量同步，主节点生成RDB文件发送给从节点；全量同步完成后采用增量同步，主节点将写操作记录在缓冲区并发送给从节点。

主从复制的工作流程是从节点向主节点发送同步命令，主节点根据情况进行全量或增量同步，从节点接收并处理数据。其特点和作用包括读写分离、数据备份和提高可用性。

优点：高可靠性 ，在master数据库出现故障后，可以切换到salve数据库；读写分离，主节点负责处理写操作，从节点负责处理读操作，有效应对大并发量的读写操作

缺点：不具备自动容错和恢复能力，主节点故障，从节点需要手动升为主节点，可用性较低

Redis是如何保证主从服务器一直处于连接状态以及命令是否丢失?命令传播阶段，从服务器会利用心跳检测机制定时的向主服务发送消息。

因为网络原因在主从复制过程中停止复制会怎么样？如果出现网络问题断开，会自动重连，并且支持断点续传，接着上次复制的地方继续复制，而不是重新复制一份。

Redis主从架构丢失数据主要有两种:异步复制导致的数据丢失(Redis主节点和从节点的复制是异步的，当主节点的数据未完全复制到从节点时就会发生宕机了，master内存中的数据会丢失)、集群产生脑裂(一个集群中有多个主节点，像一个人有两个大脑，到底听谁的)

如何保证主从复制的高可用性（主从复制中主节点挂掉怎么办）？

手动故障转移：在主节点挂掉后，人工指定一个从节点晋升为主节点，其他从节点重新配置，指向新的主节点。但这种方式响应慢，易出错。

自动故障转移：引入Sentinel系统。

### Redis哨兵模式

为了解决主从模式的Redis集群不具备自动容错和恢复能力的问题，Redis从2.6开始提供哨兵模式

哨兵模式的核心还是主从复制，它由多个哨兵节点组成分布式系统，用于监控Redis主从节点的运行状态，并在主节点出现故障时自动进行故障转移。

哨兵集群作用：哨兵节点会不断监控主从节点的运行状态，检查节点是否可达、是否正常工作。向其他节点发送通知、故障转移

故障切换：如果主节点发生故障，哨兵会自动从从节点中选举一个新的主节点，并将其他从节点重新配置为新主节点的从节点。同时那台有问题的旧主也会变成新主的从节点，也就是说当旧的主节点即使恢复时，并不会恢复原来的主节点身份，而是作为新主节点的一个从节点。

工作原理是哨兵节点先判断节点是否主观下线，再通过多个哨兵节点达成共识判断节点是否客观下线，之后选举新主节点并完成故障转移。

优点： 哨兵模式是基于主从模式的，解决主从模式中master故障不可以自动切换master的问题。

缺点：浪费资源，集群里所有节点保存的都是全量数据，数据量过大时，主从同步会严重影响性能。 只有一个master库执行写请求，写操作会单机性能瓶颈影响。

### Cluster集群模式

Cluster集群模式，实现了Redis的分布式存储，对数据进行分片。Redis Cluster集群节点最小配置6个节点以上（3主3从），其中主节点提供读写操作，从节点作为备用节点，不提供请求，只作为故障转移使用。 Redis Cluster采用虚拟槽分区，所有的键根据哈希函数映射到0～16383个整数槽内，每个节点负责维护一部分槽以及槽所印映射的键值数据。

如何判断key在哪个实例？根据key的有效部分计算哈希值对16384取余，余数为插槽

如何将同类数据保存到同一redis实例?使用相同的有效部分，例如key以{typeid}为前缀

### Redis的分区

Redis分区的作用是什么？

扩展数据库容量，可以利用多台机器的内存构建更大的数据库

扩展计算能力，分区可以在多核和多计算机之间弹性扩展计算能力，在多计算机和网络适配器之间弹性扩展网络带宽

你知道有哪些Redis分区实现方案？

常见的Redis分区实现方案有客户端分区、代理分区和查询路由。

客户端分区由客户端直接决定数据存储的节点，实现简单但客户端需了解节点信息，适用于小规模集群。代理分区引入代理层转发请求，对客户端透明，但代理可能成为瓶颈，适用于中等规模集群。查询路由如Redis Cluster，客户端随机连接节点，节点负责路由请求，扩展性和容错性好，适用于大规模集群。将请求发送到任意节点，接收到请求的结点会将查询请求发送到正确的结点上执行。

Redis分区存在一些缺点。首先，数据分散管理困难，数据备份、恢复、查找和调试的难度和工作量增加。其次，跨节点操作复杂，事务操作和聚合操作难以实现。再者，扩展性受限，动态调整分区困难，可能影响服务可用性。最后，故障处理难度增加，单个分区故障影响大，恢复时数据一致性难以保证。添加删除节点复杂、数据处理复杂。不支持多个键的操作、不支持多个键的事务、

Redis高可用方案如何实现？

数据持久化、主从模式、哨兵模式、Redis集群（自研及Redis Cluster）

### 分布式锁

分布式锁则是为了保证在分布式场景下，共享资源在同一时刻只能被同一个线程访问，或者说是用来控制分布式系统之间同步访问共享资源。

分布式锁具有哪些特性？

互斥性：在任意时刻，同一条数据只能被一台机器上的一个线程执行

高可用性：当部分节点宕机后，客户端仍可以正常地获取锁和释放锁

独占性：加锁和解锁必须同一台服务器执行，不能在一个服务器上加锁，在另一个服务器上释放锁

防锁超时：如果客户端没有主动释放锁，服务器会在一定时间后自动释放锁， 防止客户端宕机或者网络异常导致宕机

分布式锁的实现方式：

基于关系型数据库：与Redis的SETNX类似，创建一个分布式锁表，加锁后就在表中添加一行记录，释放锁就删除

基于Redis：SETNX：如果不存在就设置；SETEX：可以设置超时时间

通过SETNX设置key-value获得锁，随即进入死循环，每次循环判断，如果存在key就继续循环，如果不存在key就跳出循环，当前任务执行完成后就删除以释放锁。可能会死锁

分布式锁缺陷：单点故障问题、锁过期时间、锁续期问题、可重入性

Redis实现分布式锁

客户端请求锁时，尝试在Redis中设置一个键（通常是锁的标识），并设置一个过期时间。如果设置成功，表示获得了锁；如果设置失败，表示锁已经被其他客户端持有。持有锁的客户端在使用完共享资源后，应该删除这个键，以释放锁。要避免因为网络问题或客户端崩溃导致锁无法被释放，通常会在设置锁时同时设置一个过期时间。

改进1：设置超时时间，可能出现超时时间短就提前释放锁的情况

改进2：超时时间+标识+守护线程：为每个进程和锁加个uuid标识，相同时才能释放锁，在加锁时设置预估时间，并开启个守护线程，定时检测锁的失效时间，快过期自动续期

改进3：计数 统一进程可以重复获取锁，

改进4：客户端轮询 查看其他线程是否释放了锁

Redlock获取锁的步骤：当使用多个Redis节点时，为了提高分布式锁的可靠性，在多个独立Redis实例上依次获取锁，当在大多数（N/2 + 1）实例上成功获取到锁时，才认为获取锁成功。获取锁时记录时间，判断剩余过期时间，执行完业务后释放所有实例上的锁。

假设有N个redis节点，这些节点之间既没有主从，也没有集群关系。

客户端用相同的key和随机值在N 个节点上请求锁，请求锁的超时时间应小于锁自动释放时间。

当在（N/2+1）个（超过半数）redis上请求到锁的时候，才算是真正获取到了锁。

如果没有获取到锁，则把部分已锁的redis释放掉。

失败重试：当客户端无法获取到锁时，应该在随机时间后重试，并且理想的客户端应该并发地将所有命令用时发给所有Redis实例。对于已经获取锁的客户端要在完成任务后及时释放锁，这样其他客户端就不需要等锁自动过期后在获取。如果在获取锁后，在主动释放锁前无法连接到Redis实例，就只能等锁自动失效了。

### 缓存问题

缓存雪崩是指在某一个时刻出现大规模的缓存失效的情况，大量的请求直接打在数据库上面，可能会导致数据库宕机，如果这时重启数据库并不能解决根本问题，会再次造成缓存雪崩。

原因：Redis宕机了或很多key采取了相同的过期时间

为避免Redis宕机造成缓存雪崩，可以搭建Redis集群

尽量不要设置相同的过期时间，例如可以在原有的过期时间加上随机数

使用熔断机制，限流降级。当流量到达一定的阈值时，就直接返回“系统繁忙”之类的提示，防止过多的请求打在数据库上，这样虽然难用，但至少可以使用

加互斥锁

缓存雪崩是大规模的key失效，而缓存击穿是一个热点的Key，有大并发集中对其进行访问，突然间这个Key失效了，导致大并发全部打在数据库上，导致数据库压力剧增，这种现象就叫做缓存击穿。 比较经典的例子是商品秒杀时，大量的用户在抢某个商品时，商品的key突然过期失效了，所有请求都到数据库上了。

解决：热点key不设置过期时间，避免key过期失效；加锁，如果缓存失效的情况，只有拿到锁才可以查询数据库，降低了在同一时刻打在数据库上的请求，防止数据库宕机，不过这样会导致系统的性能变差。

缓存穿透是指用户的请求在缓存中和数据库中都不存在，缓存永远都不会生效，但这些请求会穿透缓存层直接请求到数据库上了，造成数据库IO性能浪费，或者用户恶意伪造大量不存在的key进行请求，都可以绕过缓存，导致数据库压力太大挂掉。

解决方法：将无效的key存放进Redis中；参数校验，例如可以对用户id进行校验，直接拦截不合法的用户的请求；使用布隆过滤器，预加载数据库中可能存在的数据，查询时先判断数据是否存在：如果布隆过滤器判定某个 key 不存在布隆过滤器中，那么就一定不存在，如果判定某个 key 存在，那么很大可能是存在(存在一定的误判率)。于是我们可以在缓存之前再加一个布隆过滤器，将数据库中的所有key都存储在布隆过滤器中，在查询Redis前先去布隆过滤器查询 key 是否存在，如果不存在就直接返回，不让其访问数据库，从而避免了对底层存储系统的查询压力。造成这种现象的原因是因为布隆过滤器中使用了hash算法，对key进行hash时，不同的key的hash值一定不同，但相同的hash的值不能说明这两个key相同。

### 如何保证缓存与数据库双写时的数据一致性？

强一致性：当更新操作完成之后，任何多个后续进程或者线程的访问都会返回最新的更新过的值。强一致性对用户比较友好，但对系统性能影响比较大。

弱一致性：系统并不保证后续进程或者线程的访问都会返回最新的更新过的值。

最终一致性：也是弱一致性的一种特殊形式，系统保证在没有后续更新的前提下，系统最终返回上一次更新操作的值。

先更新数据库，后删除缓存

这种方案也存在一个问题，如果更新数据库成功了，删除缓存时没有成功，那么后面每次读取缓存时都是错误的数据。解决这个问题的办法是删除重试机制，常见的方案有利用消息队列和数据库的日志

还有一种情况：缓存刚好失效；请求A查询数据库，得一个旧值；请求B将新值写入数据库‘请求B删除缓存；请求A将查到的旧值写入缓存。但这种情况很少，因为读远比写操作快得多 延迟双删或消息队列。就是为保证A操作已经完成，最后再删除一次缓存 即在更新数据库之后，先延迟等待一会儿（等待时间参考该读请求的响应时间+几十毫秒），再继续删除缓存。

先删除缓存，后更新数据库

这种方案也存在一些问题，比如在并发环境下，有两个请求A和B，A是更新操作，B是查询操作

1.假设A请求先执行，会先删除缓存中的数据，然后去更新数据库

2.B请求查询缓存发现为空，会去查询数据库，并把这个值放到缓存中

3.在B查询数据库时A还没有完全更新成功，所以B查询并放到缓存中的是旧的值，并且以后每次查询缓存中的值都是错误的旧值

在实际应用中，还是先更新数据库后删除缓存这种方案用的多些。写操作比读操作更耗时，（写要加锁，读可用mvcc） 还可用异步更新缓存，即写操作只更新数据库然后通过消息队列等来通知缓存更新，不过复杂性高

### HTTP状态码301和302的区别，都有哪些用途？

HTTP状态码301表示永久重定向，302表示临时重定向。二者的区别主要体现在浏览器和搜索引擎的处理方式上。对于301重定向，浏览器会记住这个重定向关系，下次请求相同资源时会直接访问新URL，搜索引擎爬虫也会更新索引，将旧URL的排名等信息转移到新URL上。而302重定向只是临时的，浏览器下次仍会向原URL发送请求，搜索引擎通常也不会更新对旧URL的索引。

301重定向常用于网站迁移、资源整合等场景，以保留旧URL的流量和搜索引擎排名。302重定向则适用于临时维护、测试新页面等情况，在不影响旧页面正常访问的前提下，将部分用户引导到新的URL。

### HTTP请求转发和重定向的区别

请求转发和重定向都是为了将客户端的请求导向其他资源，但方式不同。

请求转发：是服务器内部的操作。当服务器接收到客户端的请求后，在服务器端将请求转发到另一个资源进行处理，客户端并不知道请求被转发了。这个过程在服务器内部完成，只产生一次HTTP请求。

重定向：服务器返回一个特殊的响应（如301、302状态码）给客户端，告诉客户端需要重新向另一个URL发送请求。客户端接收到响应后，会自动发起新的HTTP请求到指定的URL。因此，重定向会产生至少两次HTTP请求。

请求转发的客户端的请求地址不会改变；重定向的客户端的请求地址会变为重定向后的URL。请求转发适用于服务器内部的资源整合和处理流程的分工，比如将一个复杂的请求拆分成多个小的处理步骤，依次转发处理。重定向：常用于URL变更、页面跳转、负载均衡等场景。例如，网站改版后将旧的URL重定向到新的URL。

### HTTP长连接和短连接，流水线是什么

HTTP短连接是指客户端与服务器每进行一次HTTP操作就建立一次连接，操作完成后断开连接，每次请求都要经历TCP连接的建立和断开过程，开销较大。

HTTP长连接是指在一次TCP连接上可以进行多次HTTP请求和响应的交互，连接在一段时间内保持打开，避免了频繁建立和断开连接的开销，HTTP 1.1默认使用长连接。

HTTP流水线是基于长连接的一种优化技术，允许客户端在未收到前一个请求的响应时就连续发送多个请求，服务器按请求顺序依次处理并返回响应，能进一步提高传输效率，但可能存在队头阻塞问题。

### OPTIONS请求方法及使用场景

### POST和PUT请求的区别

POST和PUT请求在HTTP协议中有以下区别： 语义上，POST通常用于向服务器提交数据以创建新资源或追加数据到已有资源，而PUT用于完整地替换目标资源。 幂等性方面，POST不是幂等的，多次相同的POST请求可能会创建多个资源；PUT是幂等的，多次相同的PUT请求对同一资源的影响相同。 应用场景上，POST适用于创建新资源的场景，如用户注册、订单提交等；PUT更适合更新已有资源，如修改用户信息、更新商品库存等。 URL语义上，POST的URL通常指向集合资源，PUT的URL通常指向具体的资源实例。

### TCP 和 UDP 分别对应的常见应用层协议有哪些？TCP 是如何实现流量控制的？

流量控制是 TCP 的一个重要机制，用来 防止发送方发送过快，导致接收方处理不过来而丢包。不同于“拥塞控制”（防止网络过载），流量控制只关心接收方的处理能力。

TCP通过滑动窗口机制实现流量控制。接收方会维护一个接收窗口，该窗口大小表示接收方当前接收缓冲区的可用空间。接收方在发送确认信息时，会在TCP头部的窗口字段中通告自己的接收窗口大小给发送方。

发送方根据接收方通告的窗口大小来调整自己的发送窗口，决定可以发送但未收到确认的数据量。随着数据的接收和处理，接收方会动态调整通告的窗口大小，当接收方处理速度变快、接收缓冲区可用空间增加时，增大窗口大小；反之则减小窗口大小。

如果接收方缓冲区满了，为了防止“死锁”，TCP 会启动 零窗口探测。

### TCP的拥塞控制机制

当网络中某一资源的需求超过了该资源所能提供的可用部分时，网络性能就要变坏，这种情况就叫做拥塞。在TCP中，如果发送方发送数据过快，会导致网络拥塞。

TCP拥塞控制通过调整发送方的发送窗口大小来控制发送速率。发送窗口的大小取决于两个因素：接收方的接收能力（由接收窗口rwnd表示）和网络的拥塞状况（由拥塞窗口cwnd表示），实际的发送窗口大小取rwnd和cwnd中的最小值。

慢开始算法在开始发送数据时，将拥塞窗口以指数级增长，快速试探网络的可用带宽；当拥塞窗口达到慢开始门限后，进入拥塞避免阶段，拥塞窗口以线性方式增长，避免增长过快导致网络拥塞。如果发生超时重传，说明网络出现严重拥塞，将慢开始门限和拥塞窗口重置，重新开始慢开始算法。如果收到3个重复的确认报文，执行快重传和快恢复算法，快速恢复丢失的报文段，发送方将慢开始门限和拥塞窗口减半，并执行拥塞避免算法。

当cwnd < ssthresh时，使用慢开始算法；

当cwnd > ssthresh时，停止使用慢开始算法而改用拥塞避免算法；

当cwnd = ssthresh时，既可以使用慢开始算法，也可以使用拥塞避免算法；

### 什么是流量控制？

流量控制，用来管理发送方和接收方之间的数据传输速率，以防止因接收方处理能力不足而导致的数据包丢失或网络拥塞。常用的流量控制方法有停止-等待协议和滑动窗口协议。它能保证数据传输的可靠性，提高网络资源的利用率。

需要注意的是，流量控制与拥塞控制不同，前者是点对点的控制，后者针对整个网络。

### 对 WebSocket 的理解

WebSocket 是一种在单个 TCP 连接上进行全双工通信的协议。它允许浏览器和服务器之间进行实时通信，一旦连接建立，双方可以在任意时刻向对方发送数据。

### 对keep-alive的理解

在TCP层面，keep - alive机制在一段时间无数据传输时发送探测包检测对端是否可达，如果在一定次数的探测后没有收到响应，就认为连接已经断开并关闭，能节省资源。

HTTP协议中的keep - alive允许在一个TCP连接上进行多次HTTP请求和响应，而不是每次请求都重新建立连接。减少了TCP连接、释放的开销

### 迭代查询与递归查询

迭代查询和递归查询是计算机网络中DNS查询的两种主要方式。迭代查询中，客户端向DNS服务器发送请求，若服务器无所需信息则返回其他服务器地址，客户端继续向新服务器查询，直至得到结果。此方式客户端承担较多查询工作，减轻了服务器负担，但查询效率相对较低，适用于对服务器资源消耗有严格限制或客户端处理能力较强的场景。

递归查询中，客户端向DNS服务器发送请求后，服务器代替客户端完成后续查询并返回结果。客户端较为轻松，但服务器负担重，查询效率一般较高，适用于客户端处理能力弱或对查询效率要求高的场景。在实际应用中，需根据具体情况选择合适的查询方式。

### 页面有多张图片，HTTP是怎样的加载表现？

在HTTP/1.0中，每次请求都要建立新的TCP连接，浏览器会为每张图片依次发起独立请求，存在大量连接开销，加载时间长。

HTTP/1.1支持持久连接，浏览器会根据并发请求限制将图片请求分配到多个TCP连接上并行发送，但存在队头阻塞问题，若某个请求被阻塞，后续请求需等待。

HTTP/2采用多路复用技术，允许在一个TCP连接上同时并行发送多个请求和接收多个响应，不存在队头阻塞，还通过头部压缩降低传输开销，能显著提高图片加载效率。

### 完整性约束包括哪些？

MySQL 中的完整性约束包括实体完整性、域完整性、参照完整性和用户定义的完整性。实体完整性通过主键约束和唯一约束确保表中记录的唯一性；域完整性通过数据类型、检查约束、默认值约束和非空约束保证列中数据符合特定规则；参照完整性通过外键约束维护不同表之间数据的一致性；用户定义的完整性则根据用户的业务需求自定义，可通过触发器或存储过程实现。

### mysql 中in 和exists 的区别 在 MySQL 里都能实现子查询

· 执行逻辑：In会先执行子查询 (SELECT d.id...)，生成一个结果集（临时表）。EXISTS 先执行主查询，再带入到子查询，子查询不会真正返回结果集，而是返回布尔值（TRUE / FALSE），然后查看是否有匹配行。

语法作用：IN：用于判断某个值是否在指定的集合中；EXISTS：用于判断子查询是否返回结果（只要有一条记录即可）

Not：NOT IN 在子查询结果中 出现 NULL 时会有问题，可能导致主查询结果为空。NOT EXISTS 不受 NULL 影响，更加安全。

性能：子查询结果集较小时，in更高效；较大时，exists更高效

场景：in：适合子查询结果集较小，或需要判断 “是否在固定值列表中”。exists：子查询结果集大，或需要关联主查询表时。

### MySQL 是如何保证主备同步？主从复制

MySQL通过以下方式保证主备同步：首先，主库将数据变更操作记录到二进制日志（binlog）中。备库的I/O线程与主库建立连接，从主库获取二进制日志内容并写入本地的中继日志（relay log），备库的SQL线程再从中继日志中读取内容并在备库上执行，从而实现数据同步。

服务器记录日志：所有对数据库的数据更改都会记录到主服务器的二进制日志中。

从服务器请求日志：从服务器的 IO 线程定期向主服务器请求二进制日志的更新。

主服务器发送日志：主服务器将自己的二进制日志发送给从服务器。

从服务器执行日志：从服务器通过 IO 线程从主服务器获取二进制日志并将其写入本地中继日志（Relay Log）。SQL 线程从中继日志中读取 SQL 语句并在从服务器上执行，以达到数据同步。

MySQL支持异步复制、半同步复制和全同步复制三种模式，可根据不同的需求选择合适的模式。同时，MySQL具备异常处理机制，当网络异常时，备库会尝试重新连接主库并从断点处继续同步；主库故障时，可将备库提升为主库；遇到数据冲突时，会根据错误信息进行相应处理。

全同步复制，就是当主库执行完一个事务之后，要求所有的从库也都必须执行完该事务，才可以返回处理结果给客户端。异步复制，就是当主库提交事务后，会通知 binlog dump 线程发送 binlog 日志给从库，一旦 binlog dump 线程将 binlog 日志发送给从库之后，不需要等到从库也同步完成事务，主库就会将处理结果返回给客户端。半同步复制的方式：原理是在客户端提交事务之后不直接将结果返回给客户端，而是等待至少有一个从库收到了 Binlog，并且写入到中继日志中，再返回给客户端。

高可用性和故障转移、负载均衡、数据备份

二进制日志（Binary Log）：主服务器记录所有对数据库的更改（如 INSERT、UPDATE、DELETE 操作）到二进制日志中。该日志是基于事件的，记录了对数据库的所有修改操作。

redo log（重做日志）是一种用于保障数据一致性的日志机制。Redo log记录了对数据库的每一个修改操作，确保在系统崩溃后可以通过这些日志恢复未保存的更改。

### MySQL 是如何保证数据不丢失的？

Redo log 保障 “崩溃恢复” 的数据持久化

&nbsp;InnoDB 存储引擎独有的物理日志，记录的是 “数据页的物理修改操作”，与具体表结构无关。InnoDB 采用 Write-Ahead Logging（WAL） 原则：先写 redo log，再修改内存数据。redo log 文件是固定大小的循环文件，写满后覆盖旧日志。 事务修改时写 buffer，提交时刷盘

undo log（回滚日志）：保障 “事务回滚” 与 “MVCC”

undo log 是 InnoDB 存储引擎独有的逻辑日志，记录的是 “数据修改前的原始状态”。事务私有：每个事务有独立的 undo log，事务提交后不会立即删除；InnoDB 独有：仅 InnoDB 支持事务和 MVCC，因此只有 InnoDB 有 undo log。 事务修改时同步写入

binlog（二进制日志）：保障 “数据备份” 与 “主从同步”

binlog 是 MySQL 服务器层的逻辑日志（所有存储引擎通用），记录的是 “引起数据变更的 SQL 语句的逻辑含义”。追加写入：binlog 文件是按顺序追加的，写满一个后自动生成新文件（不会覆盖旧文件）。服务器层日志：所有存储引擎（InnoDB、MyISAM 等）都支持，由 MySQL 服务器统一管理。 事务提交时刷盘

MySQL通过多种机制保证数据不丢失。首先，InnoDB存储引擎使用重做日志，事务操作会先记录到重做日志缓冲区，再按规则刷入磁盘的重做日志文件，崩溃时可据此恢复已提交事务。二进制日志记录数据库的更改操作，用于主从复制和增量恢复。

### MySQL中有哪几种锁？

根据粒度分：

行级锁（Row-Level Locks）：对一行记录进行加锁，允许其他事务同时访问其他行。适用于高并发的环境，能够提高并发性能。开销大，加锁慢，会出现死锁

InnoDB的行锁是通过给索引上的索引项加锁实现的，如果没有索引，InnoDB将通过隐藏的的聚簇索引来对记录进行加锁。

分为：

共享锁（S锁）：允许其他事务读取，但不允许修改。

排他锁（X锁）：禁止其他事务读取和修改。

表级锁（Table-Level Locks）：对整张表进行加锁，其他事务在锁定期间无法对该表进行任何的写入操作。适用于简单查询和不需要高并发的场景。开销小，加锁快，不会出现死锁

页级锁：锁定粒度介于表级锁和行级锁之间，开销和加锁时间界于表锁和行锁之间，会出现死锁；并发度一般。适用场景：目前使用相对较少。

根据类别分：

共享锁（读锁）：多个事务可以同时对同一数据加共享锁，加锁后其他事务可以读取该数据，但不能修改。 查询时

排他锁（写锁）：一个事务对数据加排他锁后，其他事务不能再对该数据加任何类型的锁，直到该锁被释放。 更新、插入、删除时

### 讲讲你对MVCC的理解

MVCC是一种多版本并发控制机制，是一种数据库可以同时处理多个读写操作的一种特殊机制。核心思想就是每个人看到的数据版本不同，这样读数据和写数据就不会相互干扰了。比如很多人在读一本书，每个人读到的是不同版本，如果是写操作就是有人修改了这本书的内容，数据库不会直接覆盖原来的内容，而会创建一个新版本，就好比书有修订版。而对于操读作永远读的是你开始读到的那个版本，不管别人怎么修改。这样读数据的人不会因为写数据而等待，而写数据不会因为读数据而阻塞。

原理：通过为数据行维护多个版本（历史快照），让 读操作不用阻塞写操作，写操作也不用阻塞读操作。

它通过保存数据的多个版本，使得读写操作可以并发执行，避免了读写冲突，提高了数据库的并发性能。 读写不阻塞、高并发性能好、避免幻读

InnoDB 每一行数据都有一个隐藏的回滚指针，用于指向该行修改前的最后一个历史版本，这个历史版本存放在 undo log 中。如果要执行更新操作，会将原记录放入 undo log 中，并通过隐藏的回滚指针指向 undo log 中的原记录。其它事务此时需要查询时，就是查询 undo log 中这行数据的最后一个历史版本。

### 事务的实现原理 undo log、 redo log、锁、MVCC

A事务是一个不可分割的工作单位，要么全部完成，要么全部不执行。undo log事务修改时旧值写入undolog，事务失败或回滚就根据undolog恢复到原始状态，另外undolog也用于mvcc提供旧版本数据

C一致性执行前后数据库必须从一个一致性状态转到另一个一致性状态。 aid共同保证

I隔离性指的是多个事务并发执行时，并不会相互干扰。 锁+mvcc

D事务一旦提交，对数据库所做的更改将被永久保存，即使系统崩溃或出现故障。 WAL +Redolog，事务提交时先把修改写入redolog然后再刷盘，崩溃时根据redolog恢复

### 什么是数据库的乐观锁和悲观锁，如何实现？

乐观锁（读多写少场景）：系统假设数据的更新在大多数时候是不会产生的冲突的，所以数据库旨在更新操作提交的时候对数据检测冲突，如果存在冲突，则数据更新失败。

悲观锁（读少写多场景）：鉴定会发生并发冲突，屏蔽一切可能违反数据完整性的操作。通俗讲就是每次去拿数据的时候都认为别人会修改，所以每次在拿数据的时候都会加上锁（在所有操作前都加锁）。

### 什么是死锁？如何避免？

死锁是指两个或多个事务在执行过程中，因争夺锁资源而造成的一种互相等待的现象，若无外力作用，它们都将无法推进下去。

如何避免

合理设计事务、优化索引、调整隔离级别、调整事务优先级

### MySQL多表查询的连接方式

内连接（INNER JOIN）：只返回满足连接条件的记录，取两表交集。适用于只获取相关联数据的场景。

左连接/右连接（LEFT JOIN 或 LEFT OUTER JOIN）：返回左表(右表)全部记录及右表(左表)匹配记录，右表(左表)无匹配时字段值为NULL。

交叉连接（CROSS JOIN）：返回两表的笛卡尔积。用于需要生成所有可能组合的场景。

### Redis 的有序集合底层为什么要用跳表，而不用s平衡树、红黑树或者 B+树？

跳跃表（面试常问）：跳跃表是一种有序数据结构，它通过在每个节点维持多个指向其他结点的指针，从而达到快速访问节点的目的。平均O(logN)、最坏O(N)复杂度的结点查找，还可以通过顺序性操作来批量处理节点。~~跳跃表是有序集合键的底层实现之一 ，跳跃表还在集群节点中用作内部数据结构。跳跃表本质是一种空间换时间的策略，~~是一种可以进行二分查找的有序链表，~~跳跃表在原有的有序链表上增加了多级索引，通过索引来实现快速查询。~~跳表不仅能提高搜索性能，同时可以提高插入和删除操作的性能。

跳跃表相比于红黑树的优点（redis为什么用跳跃表而不是红黑树）：

内存占用更少，自定义参数化决定使用多少内存、查询性能至少不比红黑树差

简单更容易实现和维护

平衡树 vs 跳表：平衡树的插入、删除和查询的时间复杂度和跳表一样都是 O(log n)。对于范围查询来说，平衡树也可以通过中序遍历的方式达到和跳表一样的效果。但插入或删除都需要保持平衡，耗时。跳表不是严格平衡，插入删除算法简单，速度快。

红黑树 vs 跳表：相比较于红黑树来说，跳表的实现也更简单一些，不需要通过旋转和染色（红黑变换）来保证黑平衡。并且，按照区间来查找数据这个操作，红黑树的效率没有跳表高。

B+树 vs 跳表：B+树更适合作为数据库和文件系统中常用的索引结构之一，它的核心思想是通过可能少的 IO 定位到尽可能多的索引来获得查询数据。对于 Redis 这种内存数据库来说，它对这些并不感冒，因为 Redis 作为内存数据库它不可能存储大量的数据，所以对于索引不需要通过 B+树这种方式进行维护，只需按照概率进行随机维护即可，节约内存。而且使用跳表实现 zset 时相较前者来说更简单一些，在进行插入时只需通过索引将数据插入到链表中合适的位置再随机维护一定高度的索引即可，也不需要像 B+树那样插入时发现失衡时还需要对节点分裂与合并。

### 什么是内核

内核是操作系统最核心、最基础的部分，是计算机硬件和软件之间的接口。它运行在最高特权级别，负责管理系统的硬件资源，如进行进程管理（创建、调度和终止进程）、内存管理（分配和回收内存）、设备驱动（与硬件设备通信和控制）以及文件系统管理（文件的存储、读写和删除等操作）。同时，内核为上层的应用程序提供服务，应用程序通过系统调用请求内核完成各种操作。

### 什么是线程？

线程是操作系统中的一个基本执行单元，它是程序执行的最小单位。多个线程可以在同一个进程中并发执行，共享该进程的资源，如内存和文件描述符等。进程是程序在操作系统中的一次执行过程，是系统进行资源分配和调度的基本单位。一个进程可以包含多个线程。并发是指在一段时间内，多个任务交替执行；并行是指在同一时刻，多个任务同时执行。

进程与线程：

每个进程都有自己的地址空间，进程间资源隔离；线程共享进程的资源，同一进程内可彼此访问；

切换进程开销大；线程开销小

进程间通信相对复杂，要用到管道、消息队列等；线程间通信简单，因为可直接访问共享内存

作用：提高程序并发性能、充分利用多核处理器

程序是静态的，进程是动态的。程序是一组指令的集合，而进程是程序的执行过程。程序可以长期保存在磁盘上，而进程有一定的生命周期，会随着程序执行的结束而消亡。

### 什么是虚拟内存？

实际的物理内存容量是有限的，当运行多个大型程序时，物理内存可能无法同时容纳所有程序的数据和代码，这会限制系统的多任务处理能力。虚拟内存是一种计算机系统内存管理技术，它为每个进程提供独立的虚拟地址空间，进程可认为自己拥有整个内存。其工作基于分页机制，通过内存管理单元将虚拟页号映射到物理页号。当物理内存不足时，利用页面置换将暂时不用的页面换出到磁盘交换空间。

### 怎么避免死锁？

死锁是指两个或多个进程在执行过程中，因争夺资源而造成的一种互相等待的现象，若无外力作用，它们都将无法推进下去。 线程间相互等待对方释放资源，而造成的一种僵持现象。

产生死锁的必要条件：

互斥：资源不能被多个线程同时使用。

请求和保持：一个线程已经持有了至少一个资源，同时又在等待获取额外的资源。

不可剥夺：线程获得的资源在使用完之前不能被强行剥夺，只能由线程自己释放。

环路等待：存在一个循环等待链，即每个线程都在等待下一个线程所持有的资源。

互斥条件：进程对所分配到的资源进行排他性使用，即在一段时间内某资源只由一个进程占用。 通过资源虚拟化等手段将独占资源改造成共享资源

请求和保持条件：进程已经保持了至少一个资源，但又提出了新的资源请求，而该资源已被其它进程占有，此时请求进程阻塞 ，但又对自己已获得的其它资源保持不放。 采用预先静态分配法，让进程在运行前一次性申请所需的全部资源

不剥夺条件：进程已获得的资源，在未使用完之前，不能被剥夺，只能在使用完时由自己释放。 当进程提出新的资源请求不能满足时，剥夺其已占有的资源，

环路等待条件：在发生死锁时，必然存在一个进程——资源的环形链，即进程集合{P0，P1，P2，···，Pn}中的P0正在等待一个P1占用的资源；P1正在等待P2占用的资源，……，Pn正在等待已被P0占用的资源。 使用资源有序分配法，给资源编号，让进程按编号递增顺序请求资源。 还可以使用银行家算法进行动态的资源分配，系统在进行资源分配之前，先计算此次分配资源的安全性，如果分配不会导致系统进入不安全状态，则将资源分配给进程；否则，让进程等待。

进程常见的状态在不同模型下有不同的划分。在三态模型中，进程有运行态、就绪态和阻塞态。运行态表示进程正在占用CPU执行程序；就绪态表示进程已具备运行条件，等待CPU调度；阻塞态表示进程因等待某个事件（如I/O操作完成）而无法继续执行。

### 排序算法 冒险家n2（冒 选 插） 归速堆（nlogn）

冒泡排序（Bubble Sort）

原理：从数组的第一个元素开始，依次比较相邻的两个元素。如果前一个元素大于后一个元素，则交换它们的位置。每一轮遍历会将当前未排序部分的最大元素“冒泡”到末尾。重复上述过程，直到整个数组有序。

特点：简单直观，但时间复杂度较高，为o(n2)，为空间复杂度为o(1)

（2）选择排序（Selection从未排序中选择一个放到未排序第一个、已排序后边 无序

原理：将数组分为已排序部分和未排序部分。每次从未排序部分中选择最小（或最大）的元素。将该元素与未排序部分的第一个元素交换，将其放入已排序部分。重复上述过程，直到整个数组有序。

特点：无论数据初始状态如何，时间复杂度都是o(n2)，空间复杂度为o(1)。

（3）插入排序（Insertion Sort） 从未排序部分插入到已排序部分的正确位置 有序

原理：将数组分为已排序部分和未排序部分。每次从未排序部分中取出第一个元素，插入到已排序部分的正确位置。重复上述过程，直到整个数组有序。

在数据基本有序时效率较高，时间复杂度为O(n2)，空间复杂度为o(1)。

(4) 二分插入排序

二分插入排序是对插入排序的一个小小的改进：

改进的地方在于在前面已经排好序的序列中找当前要插入的元素的时候采用二分查找的方式去找那个插入的位置(大于key的那个位置)

(5) 快速排序（Quick Sort） 从大范围划分为小范围排序 || 从大到小 nlogn

描述：选择一个“基准”元素，分区操作将比基准小的元素放左边，大的放右边，然后递归地对左右子数组排序。

(6) 归并排序 递归划分两半子数组并变大排序 从小到大 nlogn

原理：将数组递归地分成两半，直到每个子数组只有一个元素。将两个有序的子数组合并成一个有序数组。重复合并过程，直到整个数组有序。

堆排序（Heap Sort） nlogn

原理：将数组构建成一个最大堆（或最小堆）。将堆顶元素（最大值）与堆的最后一个元素交换，末尾的数为最大值，剩余待排序数组个数为n-1。重新调整堆，使其满足堆的性质。重复上述过程，直到堆的大小为 1，数组有序。

二分查找（Binary Search）

原理：要求数组必须是有序的。每次将目标值与数组中间元素比较：如果目标值等于中间元素，返回其索引。如果目标值小于中间元素，在左半部分继续查找。如果目标值大于中间元素，在右半部分继续查找。重复上述过程，直到找到目标值或查找范围为空。

### Kafka是如何保证消息顺序的

### 什么是消息队列？它的作用是什么？

消息队列是一种异步通信机制，用于存储和管理消息的缓冲区。生产者将消息发送到队列中，消费者从队列中获取消息并进行处理。消息队列遵循先进先出（FIFO）的原则，确保消息按顺序被处理。 异步处理、连接生产者和消费者（解耦）、日志处理、数据同步

消息队列的作用主要有：一是解耦，生产者和消费者通过消息队列间接交互，可独立开发、部署和扩展；二是异步处理，生产者发送消息后无需等待消费者处理完成，提高系统响应速度；三是流量削峰，在高并发场景下作为缓冲区，避免后端系统崩溃；四是日志处理，将日志信息发送到队列，由专门系统处理，避免影响业务系统性能。

消息队列中间件是一种专门用于实现消息队列功能的中间件软件。它作为消息的载体，在不同的应用程序、服务或系统之间传递消息。常见的消息队列中间件有RabbitMQ、Kafka、ActiveMQ等。

### Kafka的消费消息传递过程

首先，生产者根据分区策略将消息发送到主题的特定分区，消息会被追加到分区的日志文件中，并且分区有副本保证数据可靠性。

工作流程：

Kafka的工作流程主要涉及生产者、Kafka集群和消费者三个部分。生产者将消息序列化后，根据分区策略将消息发送到Kafka集群中对应分区的leader副本所在的broker。Kafka集群接收到消息后，将其追加到对应分区的日志文件中，并复制到其他follower副本以保证数据冗余和高可用性，同时将消息持久化到磁盘。消费者以消费者组的形式订阅主题，Kafka的组协调器会为消费者组内的消费者分配分区，每个分区只能被一个消费者消费。通过记录消费偏移量跟踪消费位置，主动从Kafka broker拉取消息进行消费。消费者消费消息后，需要向Kafka发送消费确认，更新偏移量。

### 基础架构

Producer（生产者）：负责向Kafka的Topic（主题）中发送消息。Consumer（消费者）：从Kafka的Topic中读取消息。Broker是Kafka集群中的服务器节点，Broker负责存储和管理消息，接收生产者发送的消息并存储到磁盘，同时为消费者提供消息读取服务。Topic（主题）：是Kafka中消息的逻辑分类，生产者将消息发送到特定的Topic。Partition（分区）：分区是物理存储单元，每个Topic可以分为多个分区。分区可以分布在不同的Broker上，实现数据的分布式存储，每个分区是一个有序的消息序列。

### 简述RabbitMQ与Kafka选型对比 ？

RabbitMQ：是一个功能强大、灵活的开源消息代理，基于AMQP（高级消息队列协议），支持多种消息模式。Kafka：是一个分布式流处理平台以高吞吐量、低延迟和可扩展性著称。

性能：Kafka吞吐量高、延迟低，适合处理海量数据；RabbitMQ吞吐量相对低些，在中小规模场景能满足需求。

可靠性：两者都支持消息持久化和确认机制，但RabbitMQ的确认机制更细致。

功能特性：RabbitMQ支持多种消息模式，适合复杂业务；Kafka侧重于发布 - 订阅模式，保证分区内消息顺序。

易用性：RabbitMQ配置管理简单，有直观界面；Kafka相对复杂。

扩展性：Kafka水平扩展性好；RabbitMQ集群部署大规模扩展时可能有性能瓶颈。

隔离级别

- 读未提交：允许一个事务读取另一个事务尚未提交的数据。

脏读：事务 A 读到了事务 B 还未提交的数据。 危害：如果事务 B 回滚，A 读到的数据就是无效的。

- 读已提交：一个事务只能读取另一个事务已经提交的数据

不可重复读：在同一事务内，两次读取同一行数据，结果不一致。 其他事务在中间修改并提交了数据。

- 可重复读：在一个事务内，多次读取同一数据时，其结果始终保持一致，即使其他事务对该数据进行了修改并提交

幻读：在同一事务内，两次读取满足条件的多行数据，结果不一致（行数变了）。其他事务插入或删除了符合条件的新行

- 串行化：所有事务依次顺序执行，事务之间完全串行化，不会相互干扰。加锁强制串行，性能最差

CAS（Compare and Swap）是一种并发编程中常用的原子操作，用于解决多线程环境下的数据竞争问题。它是乐观锁算法的一种实现方式。CAS操作包含三个参数：内存地址V、旧的预期值A和新的值B。CAS的执行过程如下：

比较（Compare）：将内存地址V中的值与预期值A进行比较。

判断（Judgment）：如果相等，则说明当前值和预期值相等，表示没有发生其他线程的修改。

交换（Swap）：使用新的值B来更新内存地址V中的值。

CAS操作是一个原子操作，意味着在执行过程中不会被其他线程中断，保证了线程安全性。如果CAS操作失败（即当前值与预期值不相等），通常会进行重试，直到CAS操作成功为止。

如何保证redo log和bin log数据的一致性

在MySQL中，通过两阶段提交（2PC）来保证redo log和bin log数据的一致性。两阶段提交将事务的提交过程分为准备阶段和提交阶段。

在准备阶段，InnoDB存储引擎将事务的修改记录到redo log中，并将redo log的状态标记为“prepare”。在提交阶段，MySQL的Server层将事务的修改记录到bin log中，如果bin log写入成功，Server层会通知InnoDB存储引擎将redo log的状态标记为“commit”；如果bin log写入失败，Server层会通知InnoDB存储引擎回滚事务。

### Mysql三大日志

在MySQL中，redo log、undo log和binlog各自有不同的用途。 redo log是InnoDB存储引擎特有的日志，用于实现事务的持久性。它记录事务对数据的修改，在事务提交时将记录刷新到磁盘，数据库崩溃时可根据redo log恢复数据。 undo log用于实现事务的原子性和MVCC。事务修改数据时，先将修改前的数据记录到undo log，事务回滚时可根据其恢复数据，同时MVCC利用undo log提供数据的多个版本。 binlog是MySQL的二进制日志，用于复制和恢复。主从复制时，主服务器将写操作记录到binlog，从服务器读取并执行；数据库出现问题时，可通过binlog进行点时间恢复

InnoDB 存储引擎选用 B+ 树而非 B 树主要有以下原因：

在磁盘 I/O 效率方面，B+ 树非叶子节点只存储索引，能容纳更多索引项，树高较低，范围查询时减少了磁盘 I/O 次数。

范围查询性能上，B+ 树叶子节点的有序链表便于顺序遍历，而 B 树进行范围查询需多次中序遍历，效率较低。

B+ 树数据全部存储在叶子节点，插入和删除操作主要影响叶子节点，非叶子节点结构稳定，保证了数据的一致性和稳定性。

B+ 树所有查询都到叶子节点结束，查询路径长度确定，利于性能优化和预测。

B树适用于快速随机访问数据，如文件系统索引；B+树广泛用于数据库索引，因其能更好满足范围查询需求。

覆盖索引是一种索引优化技术，当一个索引包含了查询所需要的所有列时，就称为覆盖索引。也就是说，数据库可以直接从索引中获取查询所需的数据，而不需要再回表查询。

索引下推，它允许在索引遍历过程中，对索引中包含的字段先进行条件过滤，将不符合条件的记录提前过滤掉，减少回表的次数。

最左匹配原则

联合索引的存储结构是按照索引列的顺序依次排序的。当进行查询时，数据库会从联合索引的最左边的列开始匹配。如果查询条件中没有包含最左边的列，数据库无法利用联合索引进行快速查找。因为索引是按照最左列排序的，没有最左列的信息，就无法确定数据在索引中的大致位置。

间隙锁是MySQL在可重复读隔离级别下为解决幻读问题引入的一种锁，它锁定的是索引记录之间的间隙，防止其他事务在这些间隙插入新记录。

聚簇索引

聚簇索引是一种将数据行和对应的索引键值存储在一起的索引方式，其叶子节点存储的是实际的数据行。主键索引通常属于聚簇索引，当创建表并指定主键时，数据会按照主键的顺序进行物理存储。 维持主键顺序，频繁插入可能造成页分裂 主键精确查找、范围查询

非聚簇索引的索引和数据是分离的，索引文件和数据文件是独立的。索引中存储的是索引键值和主键值(MyISAM中存放索引键值和对应数据记录的物理地址)。 灵活性高、索引维护简单；读写并发高；需要回表

当前读指的是读取数据的最新版本，并且会对读取的数据加锁，以保证其他事务不会对这些数据进行修改，从而避免出现数据不一致的问题。快照读是指读取数据的快照版本，而不是最新版本。在事务开启时，会为该事务创建一个数据快照，事务中的查询操作读取的是这个快照中的数据，而不是最新的数据。

SQL 里 having 和 where 子句的区别和使用场景

where子句在分组操作之前执行，用于从原始表中筛选出符合特定条件的行，它不能使用聚合函数；而having子句在分组操作之后执行，用于对分组后的结果集进行筛选，它可以使用聚合函数。

主键

定义：是表中的一列或多列，用于唯一标识表中的每一行记录。一个表只能有一个主键。保证实体完整性，确保表中不会有重复的记录。同时，它还可以作为其他表的外键关联的基础。

外键

定义：是一个表中的一列或多列，它引用了另一个表的主键。保证参照完整性，确保一个表中的数据与另一个表中的数据存在关联关系。通过外键，可以建立表与表之间的联系。

索引

定义：索引基于表中的一列或多列创建，存储了这些列的值和对应的行的物理地址。通过快速定位数据所在的位置，减少数据库的I/O操作，从而提高查询性能。

为什么 MyISAM 读快

一是采用非聚集索引，索引和数据分离存储，通过索引能快速定位数据的物理地址，减少磁盘寻道时间；二是使用B-Tree索引结构，查找效率高；三是采用表级锁，读操作时多个读操作可同时进行，加锁和解锁开销小；四是数据存储方式简单，不支持事务和外键等复杂特性，减少了额外开销。

请解释TCP的粘包、拆包现象以及对应的解决方法

在TCP协议中，数据是以字节流的形式进行传输的，TCP会根据缓冲区的实际情况进行数据包的合并和发送。

粘包：指多个应用层数据包被合并成一个TCP数据包进行发送，接收方在接收时无法区分这些原始的应用层数据包。 TCP为了提高传输效率，采用Nagle算法，将多次连续发送的小数据包合并成一个大的数据包发送，从而导致粘包。接收方没有及时从接收缓冲区读取数据，后续的数据会继续存入缓冲区，导致多个应用层数据包混在一起，形成粘包。

当发送方发送的数据包过大，超过了TCP协议的最大传输单元（MTU），或者接收方的缓冲区不足以一次性接收完整的数据包时，一个完整的数据包会被拆分成多个小的数据包进行传输，接收方需要将这些小数据包重新组装成完整的数据包，这种现象称为拆包。 

定长协议：规定每个应用层数据包长度固定，发送方填充不足部分，接收方按固定长度读取数据。优点是实现简单，缺点是灵活性差，可能造成空间浪费。

分隔符协议：在每个应用层数据包末尾添加特定分隔符，接收方根据分隔符区分数据包。优点是适用于长度不固定的数据，缺点是数据中含分隔符时需转义处理。

长度前缀协议：在应用层数据包头部添加表示长度的字段，接收方先读长度字段再读完整数据。优点是灵活性高，是常用方法，缺点是实现相对复杂。

UDP一般不会粘包。因为UDP是基于数据报的协议，每个数据报都有自己的头部信息，包含数据报长度等，接收方可以根据这些信息准确分割每个数据报，不会出现多个数据报粘连的情况。

请阐述对 HTTP 缓存的理解，说明如何配置 HTTP 缓存，以及如何判断 HTTP 缓存生效

HTTP缓存是一种机制，用于减少对服务器的请求，提高网站性能和响应速度。它允许浏览器和中间代理（如 CDN）存储网页资源的副本，当再次请求相同资源时，可直接使用缓存副本，减少数据传输和服务器负载。

强缓存：浏览器直接从本地缓存读取资源，无需向服务器发送请求。通过Expires和Cache-Control两个头部字段控制。

协商缓存：浏览器先向服务器发送请求，服务器根据请求头中的信息判断资源是否有更新。若未更新，返回304状态码，让浏览器使用本地缓存；若有更新，返回新的资源。通过ETag和Last-Modified头部字段控制。

判断HTTP缓存是否生效，强缓存生效时，请求状态码为200（from disk cache）或200（from memory cache）；协商缓存生效时，请求状态码为304。同时，可通过检查请求头和响应头中的相关字段来辅助判断。

简述IO多路复用

IO多路复用是一种同步IO模型，它允许一个进程同时监视多个文件描述符（如套接字）的IO状态，当某个文件描述符就绪（可读或可写）时，通知进程进行相应的操作。进程可以在一个线程内同时处理多个IO请求，避免了多进程或多线程带来的开销。

适用于需要处理大量并发连接，但每个连接的IO操作较少的场景，如网络服务器。

HTTP/1.1、HTTP/2、HTTP/3的核心差异是什么

1.  协议基础与传输层协议，HTTP/1.1：基于TCP协议。HTTP/2：同样基于TCP协议。不过它在TCP的基础上进行了改进，以提供更高效的传输。HTTP/3：基于QUIC协议。QUIC协议结合了UDP和TCP的优点，它基于UDP，却能提供类似TCP的可靠传输。
2.  性能上，HTTP/1.1存在队头阻塞问题，串行传输效率低；HTTP/2通过二进制分帧和多路复用解决了应用层队头阻塞；HTTP/3基于QUIC协议进一步解决了传输层队头阻塞。
3.  安全性方面，HTTP/1.1本身安全性弱，需结合SSL/TLS；HTTP/2强制使用TLS 1.2及以上；HTTP/3基于QUIC集成加密机制。
4.  头部压缩上，HTTP/1.1未有效压缩头部；HTTP/2采用HPACK算法；HTTP/3采用QPACK算法进一步优化。
5.  连接建立时，HTTP/1.1和HTTP/2基于TCP，握手时间长；HTTP/3基于QUIC可实现0-RTT或1-RTT连接建立。
6.  服务器推送，HTTP/1.1：没有服务器推送功能。HTTP/2：支持服务器推送。HTTP/3：在QUIC协议的支持下，服务器推送的性能更加稳定和高效。

请简述WebSocket和HTTP的区别

WebSocket是一种在单个TCP连接上进行全双工通信的协议。它允许浏览器和服务器之间进行实时通信，一旦连接建立，双方可以随时向对方发送数据。客户端和服务器通过HTTP协议进行握手，握手成功后，连接会一直保持打开状态，直到其中一方主动关闭连接。

连接方式：HTTP是无状态的短连接，每次请求都需建立新连接；WebSocket是长连接，建立后一直保持。

通信模式：HTTP是单向的请求 - 响应模式，客户端发起请求，服务器响应；WebSocket是全双工通信，双方可同时向对方发送数据。

数据格式：HTTP请求和响应通常用文本格式，需要解析，含大量头部信息；WebSocket数据传输可以是文本或二进制，无需解码，头部信息少，更适合传输实时数据。

性能：HTTP因连接开销大，频繁请求时性能低；WebSocket减少了连接开销，实时通信性能高。

应用场景：HTTP适用于传统Web页面浏览、文件下载；WebSocket适用于实时通信，如在线聊天、实时数据推送等。

UDP 如何实现可靠传输？

确认机制：为数据包添加序列号，接收方收到后发送ACK，发送方根据ACK确认数据包是否成功传输，未收到则重传。

超时重传机制：发送方为每个数据包设置超时时间，超时未收到ACK则重传。

滑动窗口机制：发送方和接收方分别维护发送窗口和接收窗口，实现流量控制。

差错检测机制：通过校验和检测数据包是否出错，出错则丢弃并重传。

拥塞控制机制：根据网络拥塞状况动态调整发送速率。

TCP/IP协议是一个协议族，包含了一系列用于实现网络通信的协议，是互联网通信的基础。

Socket（套接字）是一种用于实现网络通信的编程接口，它可以让不同主机上的进程通通过网络进行数据交换。基于客户端-服务器C/S模式。服务器端创建一个socket并绑定到指定的地址和端口，然后监听客户端的连接请求。客户端创建一个socket并连接到服务器的地址和端口。一旦连接建立，客户端和服务器就可以通过socket进行数据的读写操作。

请详细描述从输入 URL 到页面渲染的过程

从输入 URL 到页面渲染的过程如下： 首先进行 DNS 解析，浏览器先检查本地缓存，若没有则向本地 DNS 服务器查询，本地 DNS 服务器再依次向根域名服务器、顶级域名服务器和权威域名服务器查询，最终获取到域名对应的 IP 地址。 接着使用 TCP 协议通过三次握手与服务器建立连接。 然后浏览器构建 HTTP 请求消息并发送给服务器，服务器接收到请求后进行处理，构建 HTTP 响应消息返回给浏览器。 浏览器接收到响应后，开始解析和渲染页面。先解析 HTML 构建 DOM 树，解析 CSS 构建 CSSOM 树，再将二者合并成渲染树，接着进行布局计算节点位置和大小，最后绘制到屏幕上。 最后，浏览器和服务器可以通过四次挥手关闭 TCP 连接。

对于王者荣耀这类游戏，应该使用TCP还是UDP，若使用UDP，对于击杀数这种重要数据该如何处理

对于王者荣耀这类实时竞技游戏，更适合使用UDP协议。因为这类游戏对实时性要求极高，UDP无连接、传输速度快的特点能更好地满足游戏需求，减少玩家操作的延迟，提升游戏体验。而TCP的连接建立、断开过程以及流量控制、拥塞控制机制会带来一定的延迟，影响游戏的流畅性和竞技性。

若使用UDP协议，对于击杀数这种重要数据，可以采用以下方法处理：一是确认机制，客户端发送击杀信息后等待服务器的确认消息，未收到则重新发送；二是添加序列号，服务器根据序列号判断信息是否重复或丢失，丢失时要求客户端重发；三是数据备份与校验，服务器定期备份重要数据，传输时添加校验码，校验不通过则重新传输。

什么是对称加密、非对称加密？

非对称加密使用一对密钥，即公钥和私钥，公钥公开，私钥保密。用公钥加密的数据只能用对应的私钥解密，反之亦然。它的安全性高，但计算量较大，效率较低，常见算法有RSA、ECC等，常用于身份验证、数字签名、密钥交换等场景。公钥解私钥，私钥解公钥。

对称加密是指使用相同的密钥进行加密和解密操作的加密方式。它具有效率高的优点，适合对大量数据进行加密，但密钥管理困难，一旦密钥泄露，数据安全将受到威胁，常见算法有DES、AES等，常用于文件加密、数据库加密等场景。

断点续传

实现断点续传需要客户端和服务器端协同工作。客户端方面，要记录已经下载的字节数作为断点信息，在续传时发送带有Range请求头的HTTP请求，指定从断点处开始下载，并将新下载的数据追加到本地文件的断点位置。服务器端需要支持Range请求，根据请求头中的范围信息返回文件的部分内容，并设置 Content-Range 头告知客户端返回的内容范围。

请说明 session、token、cookie 的使用场景和区别

HTTP 协议是无状态的，即服务器无法识别两次请求是否来自同一客户端。为了实现用户状态的跟踪和管理，引入了 session、token、cookie 等机制。

session：会话机制，服务器端用于跟踪用户会话状态的技术。服务器为每个客户端创建一个唯一的 session ID，通过这个 ID 来识别不同的客户端。

token：令牌，是一种身份验证和授权的方式。客户端通过某种方式获取一个令牌，后续请求携带该令牌，服务器验证令牌的有效性来确认客户端身份。

cookie：客户端存储数据的一种方式，服务器可以在响应头中设置 cookie，客户端接收到后会将其存储在本地，后续请求会自动携带这些 cookie 发送给服务器。

session 适用于对安全性要求较高、需要服务器端保存用户状态的场景，数据存储在服务器端。它相对安全，但跨域支持较差，服务器端管理 session 会占用一定资源。

token 适用于前后端分离架构和第三方登录场景，存储在客户端。具有较好的跨域支持和安全性，对服务器性能影响较小。

cookie 用于保存用户的个性化设置和简单的用户跟踪，存储在客户端。安全性较低，跨域支持有限，且会增加请求大小。

token会存在过期问题，过期需要重新登录；一般存储到本地缓存容易被截取；服务端不好控制，如果想让人强制下线会很麻烦，需要做黑名单等，体积比sessionid大，占用带宽，安全性依赖于密钥，密钥泄露容易被伪造。

请介绍CPU缓存

CPU缓存是位于CPU与内存之间的高速小容量存储器，其读写速度比主内存快很多，它的出现是为了解决CPU运算速度与内存读写速度不匹配的问题。

CPU的运算速度极快，而内存的读写速度相对较慢。这种速度上的巨大差异会导致CPU在等待从内存中读取数据时处于空闲状态，降低了CPU的使用效率。程序在执行过程中，具有时间局部性（近期被访问过的数据很可能在不久的将来再次被访问）和空间局部性（被访问数据附近的数据很可能也会被访问）。基于局部性原理，可以将近期可能会使用的数据提前存储在高速的存储区域，以提高数据的访问速度。

当CPU需要访问数据时，首先会在L1缓存中查找，如果找到则直接使用，这称为缓存命中；如果L1缓存中没有，则会到L2缓存中查找，以此类推。如果所有缓存中都没有所需的数据，就会从主内存中读取数据，并将数据同时存入各级缓存中，以便后续访问。

服务网关:确保服务提供者对客户端的透明，这一层可以进行反向路由、安全认证、灰度发布、日元控等前置动作

服务发现:注册并维护远程服务及服务提供者的地址，供服务消费者发现和调用，为保证可用性，如etcd,nacos,consul等

依赖注入：依赖注入（Dependency Injection，简称 DI）是一种设计模式，用于解耦组件之间的依赖关系，通过外部传递依赖（而非组件内部自行创建）。将对象所依赖的资源从外部提供，而不是内部自己创建。。

Wire 是 Google 官方推出的依赖注入工具，它通过代码生成（而非运行时反射）实现依赖注入，避免了反射带来的性能开销和复杂性。Wire 基于「提供者（Provider）」和「注入器（Injector）」实现依赖管理。提供者是一个函数，用于创建某个类型的实例，并声明其依赖项。注入器（Injector）：是 Wire 生成的函数，负责按依赖关系调用提供者，最终返回目标对象。

### char和varchar用作主键的话，哪一个好，为什么

char 因固定长度带来的索引效率和稳定性优势，比 varchar 更适合作为主键，但整数类型本身是主键的最佳选择。

char固定长度，长度不轻易更改，所以主键值更稳定，索引长度更简单，varchar可变长度，主键值被频繁修改，增加开销，索引结构更复杂。

int做主键，高性能、易于管理，较小的存储空间，但可读性较差并且数值范围限制

字符串做主键，可读性强，数值范围大，可容易处理特殊情况（如空值或重复值），但性能较低，存储空间较大

### 熔断和限流的区别

限流是控制流量速率，预防过载；熔断是停止无效调用，防止故障扩散。

限流是拦截 / 排队超额请求； 熔断是 断开调用，快速返回。

限流：基于 “流量指标” 触发，与依赖服务的状态无关。熔断：基于 “依赖服务的健康状态” 触发，与流量大小无关。

限流控制整体流量，熔断处理依赖故障，共同保障系统稳定性。
